# Task: Zuraffa X-Ray Plugin — Full DTD/VM-Service UI Element Mapping + Debug Overlay

You are an expert Dart/Flutter engineer. You have internet access and a sandboxed container. You do NOT have access to our private codebase, and you must not need it — this task is fully specified by the public information below.

## Mission

Build a new Zuraffa plugin called **`x-ray`** that solves two problems simultaneously:

1. **DTD / VM Service element mapping** — Every UI element generated by Zuraffa (Controllers, Views, UseCase-triggering buttons, DataSource actions, Repository calls) gets a stable, unique ID/hash so that an agent (AI or script) connected to a running Flutter app via the **Flutter Device Test Driver (DTD) protocol** or `dart:developer` **VM Service extensions** can find and interact with it programmatically (click, scroll, read state). This makes the app fully automatable from MCP tools, CI scripts, and AI agents without relying on fragile `find.text()` or accessibility labels.

2. **X-Ray debug overlay** — When the plugin is enabled (debug mode only), the app's normal UI is replaced with a grid-based debug overlay. Each section in the grid (UseCases, Repositories, DataSources, Presenters, Services, Routes) contains one button widget per generated element. Clicking a button triggers the corresponding UseCase (via the existing `api` plugin's bridges) with predetermined values, or shows the current state of the element.

Both features are part of the same `x-ray` plugin. Enable it like:
```dart
Zuraffa.enableXRay(
  useCases: true,
  dataSources: true,
  repositories: true,
  // ... per-section toggles
);
```

### Why this exists

Today, testing a UseCase at runtime requires: navigating the full UI to trigger the flow, writing integration tests, or manually calling VM Service extensions via raw websocket. With x-ray:

- **An agent connected to DTD** can immediately find the "scanBarcode" button and click it, because every x-ray-generated widget has a known semantic Key (e.g., `Key('xray::usecase::barcode_listing::scanBarcode')`).
- **A developer in debug mode** sees the overlay grid, clicks "scanBarcode", and the UseCase fires immediately with predetermined params (hooked into the `api` bridge).
- **No fragile `find.text("Scan Barcode")`** — the Key scheme is deterministic from the entity/domain name.

### Key architectural insight: "api" plugin already did the RPC layer

The `api` plugin (via `ZuraffaApiBridge`) already:
- Registers every UseCase as a `dart:developer` extension (`ext.zuraffa.<domain>.<usecase>`)
- Handles JSON parameter deserialization
- Returns serialized `Result<T, AppFailure>` responses
- Provides `_list`, `_pollStream`, `_cancelStream` meta-extensions
- Is guarded with `kReleaseMode` / `kProfileMode` checks

**X-Ray does NOT re-do RPC.** X-Ray:
1. Reads the registered endpoint catalog (via `ZuraffaApiBridge.getRegisteredEndpoints()` or the `_list` extension)
2. Generates UI widgets that call those endpoints
3. Provides stable DTD keys for every widget
4. Injects the debug overlay when enabled

### DTD (Device Test Driver) context

Flutter's Device Test Driver protocol is the standard way to drive Flutter apps from tests and scripts. The two critical behaviors:

- `hot_restart` via DTD **does NOT re-run `main()`** — so VM Service extensions registered in `main()` persist from the cold start (this is a known gotcha — know it, don't fight it)
- Widgets must have stable `Key` objects for DTD to find them. X-Ray must assign a deterministic, semantic `Key` to every generated widget in the overlay.

### Zuraffa plugin pattern (follow this exactly)

A Zuraffa plugin in `lib/src/plugins/<name>/` typically contains:
1. A `builders/` dir — code generators (if any)
2. A `capabilities/` dir — descriptor classes (if any)
3. The runtime widget/code lives in a `lib/src/plugins/<name>/` directory with a matching export in `lib/zuraffa.dart`

The `api` plugin is the closest analog — study it.

### API signatures

```dart
// ─── Activation (in lib/zuraffa.dart alongside enableOtelReporting) ───

class XRayConfig {
  final bool useCases;
  final bool repositories;
  final bool dataSources;
  final bool controllers;
  final bool presenters;
  final bool services;
  final bool routes;
  final bool endpointCatalog; // Show all registered api bridge endpoints
  final OverlayPosition overlayPosition; // topLeft, bottomRight, etc.

  const XRayConfig({
    this.useCases = true,
    this.repositories = false,
    this.dataSources = false,
    this.controllers = false,
    this.presenters = false,
    this.services = false,
    this.routes = false,
    this.endpointCatalog = true,
    this.overlayPosition = OverlayPosition.bottomRight,
  });
}

enum OverlayPosition { topLeft, topRight, bottomLeft, bottomRight }

// On Zuraffa:
static void enableXRay(XRayConfig config) { ... }

// ─── Key generation (lib/src/plugins/xray/xray_element_key.dart) ───

class XRayElementKey {
  /// e.g. `Key('xray::usecase::barcode_listing::scanBarcode')`
  static Key useCase(String domain, String useCaseName) =>
      Key('xray::usecase::${domain}::${useCaseName}');

  static Key repository(String domain, String repoName) =>
      Key('xray::repository::${domain}::${repoName}');

  static Key dataSource(String domain, String dsName) =>
      Key('xray::datasource::${domain}::${dsName}');

  static Key controller(String controllerName) =>
      Key('xray::controller::${controllerName}');

  static Key endpoint(String method) =>
      Key('xray::endpoint::$method');
}

// ─── Overlay widget ───

class XRayOverlay extends StatefulWidget {
  final XRayConfig config;
  const XRayOverlay({super.key, required this.config});
}

// ─── XRayPlugin (registry) ───

class XRayPlugin {
  static final XRayPlugin _instance = XRayPlugin._();
  factory XRayPlugin() => _instance;
  XRayPlugin._();

  bool _enabled = false;
  XRayConfig _config = const XRayConfig();

  bool get enabled => _enabled;

  void enable(XRayConfig config) { _enabled = true; _config = config; }

  List<({String method, String domain, String usecase, String returns, bool isStream})> get registeredEndpoints =>
      ZuraffaApiBridge.getRegisteredEndpoints().map((e) => (
        method: e.method,
        domain: e.domain,
        usecase: e.usecase,
        returns: e.returns,
        isStream: e.isStream,
      )).toList();

  XRayConfig get config => _config;
}
```

### Integration into a Flutter app that uses Zuraffa


| Scenario | Input / State | Expected behavior |
|---|---|---|
| User enables x-ray with `useCases: true` | Zuraffa has 10 registered UseCase endpoints (via `ZuraffaApiBridge`) | Overlay shows "UseCases" section with 10 buttons, each with Key `xray::usecase::<domain>::<method>` |

| User enables `endpointCatalog: true` | 20 registered endpoints | Shows all 20 in the "Catalog" section, each with its method name, domain, returns info, and a call button |
| An agent connects via DTD | Flutter app running with x-ray enabled | Agent can `driver.findElement(ByValueKey('xray::usecase::barcode_listing::scanBarcode'))` and `.tap()` it |
| App is running in release mode | `kReleaseMode == true` | `enableXRay()` is a no-op — no overlay, no key registration, nothing |
| DTD issues `hot_restart` | App restarts, main() NOT re-run | X-Ray state resets (it was in-memory), but the api bridge endpoints PERSIST from the cold start — this is the known DTD behavior documented in zuraffa's INSIGHTS |
