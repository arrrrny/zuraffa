The Spec Registry & Corpora system forms the backbone of zuraffa's spec-driven development workflow. It manages the lifecycle of feature specifications—from extraction and import through batch driving and provenance auditing—ensuring every line of production code traces back to a logged zfa invocation. The system comprises three interconnected layers: the **spec registry** (the canonical `specs/` tree and its templates), the **corpus** (extracted feature collections for batch processing), and the **harness** (the orchestrator that drives corpora through the TDD cycle).

## Architecture Overview

The spec registry operates as a layered contract system. At the foundation sit the [templates](#template-grammar) that define the zuraffa-1.0 spec format. Above them, the **spec registry** maintains the canonical `specs/` directory in every zfa app, where each feature directory holds a `spec.md` plus optional `plan.md`, `tasks.md`, and `tdd/` working state. The **corpus** layer imports external spec collections (such as zik_zak's 120 extracted features) into an app's registry via `zfa corpus import`, emitting a machine-readable manifest that becomes the driving contract. The **harness** layer consumes that manifest to drive features in order through `plan → run → verify`, persisting progress and recording every gap in an append-only ledger.

## Spec Registry Structure

### The Canonical specs/ Tree

Every zfa app maintains a `specs/` directory at its root. Each feature occupies a subdirectory named with a zero-padded numeric ID (e.g., `001`, `004-login-ui`). Within each feature directory, the following files may appear:

| File | Purpose | Lifecycle |
|------|---------|-----------|
| `spec.md` | The canonical feature specification | Written by import or hand-authoring; never mutated by the loop |
| `plan.md` | Derived plan (behaviors, tasks, exit classes) | Generated by `zfa tdd plan`; regenerated on spec change |
| `tasks.md` | Task breakdown with TDD markers | Generated alongside plan; consumed by `zfa tdd run` |
| `tdd/test-list.md` | Ordered behavior list for the loop | Generated; the loop's execution contract |
| `tdd/cycle-log.md` | Per-run evidence log | Appended by each `zfa tdd run` invocation |
| `tdd/run-baseline.json` | Cached failure baseline | Written by `zfa tdd run --suite-baseline`; absorbed on re-run |

The registry distinguishes between **active specs** (in the app's `specs/`, driven by the loop) and **archived specs** (in `.specify/specs/`, the repo's own development history). The active registry is the loop's input; the archive is the tool's own provenance record.

### Template Grammar

All specs conform to the **zuraffa-1.0** template version marker (`**Template Version**: \`zuraffa-1.0\``). The grammar defines these sections, in order:

1. **Template Version** — the format version pin
2. **Summary** — one-paragraph feature description
3. **Key Entities** — a table of `(Entity, Fields, Purpose)` or bullet list
4. **External Dependencies & Contracts** — a table of `(Dependency, Type, Contract, Mock Priority)`
5. **Layer Contracts** — declared interfaces per layer (Domain, Presentation, etc.)
6. **Functional Requirements** — `FR-XXX` statements with trace annotations
7. **Acceptance Scenarios** — numbered `Given/When/Then` scenarios with a `**Type**` tag (`widget`, `acceptance`, `unit`)
8. **Lanes** — optional YAML block declaring which behaviors run in which lane (CORE, SKIN, BOTH) and whether Flutter is allowed

Sources: [feature-001/spec.md](corpus/zik_zak/feature-001/spec.md#L1-L62), [spec_parser.dart](lib/src/plugins/tdd/services/spec_parser.dart#L1-L30)

### Spec Shapes

The zik_zak corpus documents five spec shapes, each representing a different level of template compliance:

| Shape | Count (zik_zak) | Characteristics |
|-------|-----------------|-----------------|
| `modern` | 16 | Full template: all sections present, lanes declared |
| `modern-no-lanes` | 12 | Modern template without the Lanes YAML block |
| `modern-undeclared` | 12 | Modern template with undeclared routes/behaviors |
| `legacy-002` | 80 | Older template format (pre-zuraffa-1.0) |
| `legacy-003` | 12 | Alternative legacy format |

## Corpus: The zik_zak Collection

### Structure

The `corpus/` directory holds two distinct corpus types:

**zik_zak/** — The primary extracted corpus of 120 feature specs. Each feature is a directory (`feature-001` through `feature-120`) containing a single `spec.md`. A `sweep.json` file records the parse/plan statistics for the entire collection, and `corpus-shapes.txt` provides a flat name→shape mapping.

**regression/** — Three differential-test fixtures (`make-baseline-cache`, `make-suite-baseline-flag`, `u2-flow`), each with an `entry.json` describing the bug scenario and a `project/` directory containing a full zfa app scaffold. These are consumed by the differential harness, not the corpus walk.

Sources: [get_dir_structure](corpus#L1-L8), [sweep.json](corpus/zik_zak/sweep.json#L1-L30)

### The Sweep File

`sweep.json` is the corpus's self-reported health record. It tracks:

- **Parse outcomes**: `clean` (113), `refused` (7), `crashed` (0) — how many specs parsed without error
- **Plan outcomes**: `clean` (98), `refused` (22) — how many plans derived successfully
- **Declared vs fallback routes**: 580 declared, 56 fallback
- **Exit class distribution**: exit0 (98), exit3 (14), exit1 (4), exit2 (4)
- **Per-feature rows**: feature name, shape, parse status, behavior count

This file is generated by the sweep tool (`tool/sweep_zik_zak_corpus.dart`) and serves as the baseline for corpus-level regression detection.

## Corpus Import: Onboarding a Spec Collection

### The Import Contract

`zfa corpus import <source>` (or `zfa setup <name> --specs <dir>`) implements spec 050-corpus-import. The operation is **verbatim, structural, and idempotent**:

1. **Scans** the source corpus for feature directories (each containing `spec.md`)
2. **Copies** each `spec.md` verbatim into `<app>/specs/<feature>/spec.md` — no content rewriting
3. **Creates** per-feature `tdd/` working directories (empty; never touches existing contents)
4. **Marks** loop-readiness using the same `SpecParser` verdict `zfa tdd plan` uses
5. **Emits** the corpus manifest at `.zfa/manifests/corpus-manifest.json`

Sources: [corpus_importer.dart](lib/src/cli/services/corpus_importer.dart#L1-L40)

### Import Outcomes

Every feature receives exactly one of four outcomes, reported per-feature:

| Outcome | Condition | Action |
|---------|-----------|--------|
| `imported` | Target spec absent | Copy source verbatim |
| `skipped` | Identical copy already present | No write |
| `divergent` | Source differs from target | Keep target; report both sha256 hashes; update only with `--force` |
| (reported) | Not loop-ready | Imported anyway; marked `not-ready` with reason |

Foreign artifacts (speckit-era `checklists/`, foreign `tdd/test-list.md`) are **ignored and reported**, never copied or converted.

Sources: [corpus_importer.dart](lib/src/cli/services/corpus_importer.dart#L44-L75), [corpus_importer.dart](lib/src/cli/services/corpus_importer.dart#L162-L200)

### The Corpus Manifest

The manifest is the contract between import and batch driving. Stored at `.zfa/manifests/corpus-manifest.json`, it contains:

```json
{
  "source_corpus": "/path/to/source",
  "imported_at": "2026-08-31T...",
  "features": [
    {"name": "feature-001", "ready": true, "reason": ""},
    {"name": "feature-002", "ready": false, "reason": "no acceptance scenarios"}
  ]
}
```

Features are sorted **lexicographically** (deterministic order). The manifest is byte-identical on re-import of the same corpus (except `imported_at`), satisfying SC-004.

Sources: [corpus_manifest.dart](lib/src/core/project/corpus_manifest.dart#L1-L105), [corpus_manifest.dart](lib/src/plugins/tdd/models/corpus_manifest.dart#L1-L126)

## The Corpus Harness

### Command Family

`zfa corpus` exposes four subcommands that together form the harness:

| Subcommand | Purpose | Spec |
|-----------|---------|------|
| `import` | Onboard a spec corpus into `specs/` | 050-corpus-import |
| `catalog` | Classify each feature CORE or SKIN | #1015 (CORPUS-WALK child) |
| `run` | Drive cataloged features through the loop | #1016 (CORPUS-WALK child) |
| `ledger` | Committed ledger as merge gate | #1017 (CORPUS-WALK child) |

Sources: [corpus_command.dart](lib/src/commands/corpus_command.dart#L28-L46)

### Catalog: CORE/SKIN Classification

Before a corpus can be walked, each feature must be classified. `zfa catalog --target <name>` resolves features from the corpus manifest (or `--source` directly), classifies each spec as **CORE** (engine seam) or **SKIN** (presentation seam), and writes the committed catalog at `corpus/catalogs/<target>.json`.

The classifier is **deterministic signal scoring**: case-insensitive word-boundary matches over the feature name + spec content. Skin signals include `view`, `route`, `widget`, `navigation`, `theme`, `scaffold`; core signals include `entity`, `usecase`, `repository`, `datasource`, `service`, `binding`, `injection`, `state`, `contract`. **Skin wins only on strict majority; a tie classifies CORE** (engine-first: the engine contract exists before a skin wraps it).

The catalog is **committed and reviewable**: regeneration preserves manual classifications for unchanged specs (the maintainer's edit sticks), and `--reclassify` discards all edits.

Sources: [corpus_catalog.dart](lib/src/cli/services/corpus_catalog.dart#L1-L50), [corpus_catalog.dart](lib/src/cli/services/corpus_catalog.dart#L242-L280)

### Walk: Driving the Corpus

`zfa corpus run --target <name> --budget N` drives every cataloged feature through the per-feature machine contract (`zfa tdd run` then `zfa tdd verify`) and classifies each result:

| Verdict | Condition |
|---------|-----------|
| `green` | Run completes AND verify gate passes |
| `partial` | Run completes but verify gate is non-pass |
| `blocked` | Feature cannot be driven (not-ready, failed run, runner misfire) |

**Unlike spec 051's STOP-ON-ROADBLOCK, the walk never stops at a failing feature.** It walks the entire corpus and reports tallies. The configurable failure budget (`partial + blocked <= budget`, default 5) is the gate. Results persist to `.zfa/corpus/walks/<target>.json`.

Sources: [corpus_walker.dart](lib/src/cli/services/corpus_walker.dart#L1-L50), [corpus_walker.dart](lib/src/cli/services/corpus_walker.dart#L148-L200)

### Ledger: The Merge Gate

The committed ledger at `corpus/ledgers/<target>.json` is the merge gate. The first run writes the baseline; every subsequent run is a **diff** against the committed ledger:

| Diff Type | Condition | CI Impact |
|-----------|-----------|-----------|
| **regression** | Committed green → partial/blocked, or green feature vanished | **CI failure (exit 1)** |
| **renewed** | Spec hash changed but feature stayed green | Not a failure (contract evolved, still holds) |
| **added** | Feature new to the walk | Not a failure (budget governs new gaps) |
| **removed** | Feature left the walk (regression when it was green) | CI failure when green |

The ledger advances (is rewritten) **only on a clean diff**. A contract-break leaves the committed ledger untouched so the break cannot be absorbed by the very run that detected it.

Sources: [corpus_walk_ledger.dart](lib/src/cli/services/corpus_walk_ledger.dart#L1-L45), [corpus_walk_ledger.dart](lib/src/cli/services/corpus_walk_ledger.dart#L100-L160)

### Progress: Resume Capability

`CorpusProgressStore` persists corpus-level state at `.zfa/corpus/progress.json` after every completed feature. It provides:

- **Atomic persistence**: temp-file + rename saves
- **Corruption gate**: malformed JSON stops with a named exception and recovery path
- **In-flight marker**: exclusive file acquisition prevents concurrent corpus runs on the same app
- **Dropped marks**: features removed from the manifest mid-stream are recorded as `dropped` (append-only audit trail)

Per-feature states: `pending` → `driving` → `done` (gate passed) / `waived` (explicit waiver) / `stopped` (roadblock).

Sources: [corpus_progress_store.dart](lib/src/plugins/tdd/services/corpus_progress_store.dart#L1-L50), [corpus_progress.dart](lib/src/plugins/tdd/models/corpus_progress.dart#L1-L50)

## Spec Parser: The Loop's Input Contract

`SpecParser` reads a `spec.md` and emits a structured behavior list. It is the single source of truth for loop-readiness: both `zfa corpus import` and `zfa tdd plan` use the same parser, so readiness marks are consistent.

The parser extracts:

- **Behaviors** from acceptance scenarios (document-wide sequential AC-IDs, not per-story numbers)
- **Manual declarations**: scenarios tagged `(manual: <owner>)` are excluded from the automated loop
- **Key entities** with fields (supporting both backticked `` `name: Type` `` and plain prose pairs)
- **External dependencies** with contracts and mock priorities
- **Layer contracts** with declared method signatures
- **Lanes** (CORE/SKIN/BOTH) with Flutter-allowed flags

A spec is **loop-ready** when it parses cleanly and contains acceptance scenarios. The parser refuses silently-empty entities (issue #1486) rather than generating vacuous green tests.

Sources: [spec_parser.dart](lib/src/plugins/tdd/services/spec_parser.dart#L1-L50)
