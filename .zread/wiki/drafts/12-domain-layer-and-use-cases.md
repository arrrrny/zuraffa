The domain layer is where Zuraffa puts the application's business rules. It is intentionally free of UI, transport, and storage concerns: a use case takes typed parameters, delegates to a repository or service, and returns a `Result<T, AppFailure>` that the presentation layer can consume without knowing how the data was fetched. Everything in this layer is either hand-written against the base classes in `lib/src/domain` or generated by the `usecase` plugin.

## Domain Layer Overview

The domain layer lives under `lib/src/domain` and contains four kinds of artifacts:

- **Use case base classes** — `UseCase`, `StreamUseCase`, `CompletableUseCase`, `SyncUseCase`, `BackgroundUseCase`, and `OsBackgroundTaskUseCase`, plus the `Loggable` mixin they share.
- **Parameter objects** — `NoParams`, `QueryParams`, `ListQueryParams`, `CreateParams`, `UpdateParams`, `ToggleParams`, `DeleteParams`, and their Zorphy-generated parts.
- **Domain entities** — Zorphy definitions under `domain/entities` (see [Entity & Zorphy Model](11-entity-and-zorphy-model)).
- **Domain services** — stateless domain services such as `CookieService`.

```mermaid
flowchart TD
    A[Presentation / Controllers] -->|call(params)| B[UseCase]
    B --> C{Base class}
    C -->|single-shot| D[UseCase&lt;T, Params&gt;]
    C -->|reactive| E[StreamUseCase&lt;T, Params&gt;]
    C -->|no value| F[CompletableUseCase&lt;Params&gt;]
    C -->|sync| G[SyncUseCase&lt;T, Params&gt;]
    C -->|isolate| H[BackgroundUseCase&lt;T, Params&gt;]
    C -->|OS-scheduled| I[OsBackgroundTaskUseCase&lt;T&gt;]
    D & E & F & G & H & I --> J[execute(...)]
    J --> K[Repository or Service]
    K --> L[Result&lt;T, AppFailure&gt;]
    L --> A
```

## Use Case Base Classes

All use cases follow the same contract: a `call(...)` entry point that wraps `execute(...)` in a `Result`, dispatches hooks at three phases, reports failures to the registry, and supports cooperative cancellation.

| Base class | Execution shape | When to use |
|---|---|---|
| `UseCase<T, Params>` | `Future<Result<T, AppFailure>>` | Single-shot async operations (get, create, update, …) |
| `CompletableUseCase<Params>` | `Future<Result<void, AppFailure>>` | Operations with no return value (delete, logout) |
| `StreamUseCase<T, Params>` | `Stream<Result<T, AppFailure>>` | Reactive/multi-value operations (watch, pagination) |
| `SyncUseCase<T, Params>` | `Result<T, AppFailure>` (synchronous) | Validation, calculation, transformation |
| `BackgroundUseCase<T, Params>` | `Stream<Result<T, AppFailure>>` | CPU-intensive work moved to a separate isolate |
| `OsBackgroundTaskUseCase<T>` | `Future<T> execute(NoParams)` | OS-scheduled background work (workmanager) |

`UseCase.call()` is the canonical entry point. It captures the active trace context, dispatches `HookPhase.pre`, checks cancellation, calls `execute`, and on success dispatches `HookPhase.success` and returns `Result.success(value)`. On `CancelledException` it returns `CancellationFailure`; on `AppFailure` it reports and returns `Result.failure(e)`; on any other exception it wraps via `AppFailure.from(e, stackTrace)` and reports. `StreamUseCase.call()` is an async generator that does the same per emitted value and completes the stream after a failure.

Sources: [usecase.dart](lib/src/domain/usecase.dart#L30-L190), [stream_usecase.dart](lib/src/domain/stream_usecase.dart#L30-L120), [sync_usecase.dart](lib/src/domain/sync_usecase.dart#L14-L75)

## Error Handling & Result

`Result<S, F>` is a sealed `Either`-style type with `Success` and `Failure` variants. It supports `fold`, `map`, `mapFailure`, `flatMap`, `getOrElse`, `getOrNull`, `getOrThrow`, `onSuccess`, and `onFailure`. Use cases always return `Result<T, AppFailure>`, so callers pattern-match on a closed failure hierarchy rather than catching exceptions.

`AppFailure` is a sealed class with named factories: `server`, `network`, `cache`, `validation`, `notFound`, `unauthorized`, `forbidden`, `conflict`, `timeout`, `cancellation`, `unknown`, `state`, `type`, `unimplemented`, `unsupported`, `platform`. `AppFailure.from(error, stackTrace)` classifies an arbitrary exception into one of these. Every use case reports failures through `FailureReporterRegistry.instance.reportFailure(...)`, which enqueues them into a batch queue for registered reporters (e.g., OTel) — fire-and-forget and never throwing.

Sources: [result.dart](lib/src/core/result.dart#L20-L80), [failure.dart](lib/src/core/failure.dart#L20-L120), [failure_reporter_registry.dart](lib/src/core/failure_reporter_registry.dart#L100-L160)

## Cancellation

`CancelToken` provides cooperative cancellation. It tracks `isCancelled`, exposes an `onCancel` stream, and `throwIfCancelled()` raises `CancelledException`. Tokens can be linked into parent/child trees (`linkTo`, `createChild`), timeout-based (`CancelToken.timeout`), or future-based (`CancelToken.fromFuture`). Every use case accepts an optional `cancelToken` parameter and checks it before and during execution. `StreamUseCase` also applies `withCancellation(cancelToken)` to the source stream when a token is provided.

Sources: [cancel_token.dart](lib/src/core/cancel_token.dart#L1-L120)

## Hooks & Observability

Use cases dispatch to the global `HookRegistry` at three phases: `pre`, `success`, and `failure`. A `Hook` declares `id`, `priority`, `phases`, `shouldTrigger`, and `execute(HookContext, HookPhase)`. Hooks are fire-and-forget — exceptions are caught and logged, never propagated. `HookContext` carries `useCaseName`, `params`, `result`, `failure`, `duration`, `timestamp`, `traceId`, `spanId`, and a mutable shared `metadata` bag for cross-phase data. Trace IDs come from `TraceObserver.instance` (no-op by default; the `zuraffa_observability` companion swaps in a vendor-backed observer at startup).

Sources: [hook.dart](lib/src/core/hook.dart#L40-L196), [hook_registry.dart](lib/src/core/hook_registry.dart#L1-L110), [trace_observer.dart](lib/src/core/trace_observer.dart#L1-L36), [usecase.dart](lib/src/domain/usecase.dart#L40-L130)

## Parameter Types

Use cases are parameterized by a `Params` type. Zuraffa ships a closed set of parameter objects, all Zorphy-generated, so repository and use case signatures stay aligned:

| Param | Shape | Used by |
|---|---|---|
| `NoParams` | sentinel with no state | `get`/`watch` with no filter, `OsBackgroundTaskUseCase` |
| `Params` | generic map-based | custom use cases |
| `QueryParams<T>` | single-entity filter | `Get*UseCase`, `Watch*UseCase` |
| `ListQueryParams<T>` | search/filter/sort/limit/offset | `Get*ListUseCase`, `Watch*ListUseCase` |
| `CreateParams<T>` | `data: T` | custom create flows |
| `UpdateParams<I, P>` | `id`, `data` (patch) | `Update*UseCase` |
| `ToggleParams<I, F>` | `id`, `field`, `value` | `Toggle*UseCase` |
| `DeleteParams<I>` | `id` | `Delete*UseCase` (completable) |
| `InitializationParams` | repo/data source init | setup flows |

## Generated Entity Use Cases

For an entity, `zfa usecase create <Entity>` (or `zfa make`, which runs the `usecase` plugin) generates one file per method under `lib/src/domain/usecases/<domain>/`. The vocabulary is fixed:

| Method flag | Class | Base | Params | Return |
|---|---|---|---|---|
| `get` | `Get<Entity>UseCase` | `UseCase` | `QueryParams<Entity>` (or `NoParams`) | `Entity` |
| `getList` / `list` | `Get<Entity>ListUseCase` | `UseCase` | `ListQueryParams<Entity>` | `List<Entity>` |
| `create` | `Create<Entity>UseCase` | `UseCase` | `Entity` | `Entity` |
| `update` | `Update<Entity>UseCase` | `UseCase` | `UpdateParams<Id, Patch>` | `Entity` |
| `toggle` | `Toggle<Entity>UseCase` | `UseCase` | `ToggleParams<Id, Field>` | `Entity` |
| `delete` | `Delete<Entity>UseCase` | `CompletableUseCase` | `DeleteParams<Id>` | `void` |
| `watch` | `Watch<Entity>UseCase` | `StreamUseCase` | `QueryParams<Entity>` (or `NoParams`) | `Entity` |
| `watchList` | `Watch<Entity>ListUseCase` | `StreamUseCase` | `ListQueryParams<Entity>` | `List<Entity>` |

Each generated use case injects a repository (or service) via constructor, delegates to the matching repository method, and calls `cancelToken?.throwIfCancelled()` before delegating. Example (from the `Todo` sample):

```dart
class GetTodoUseCase extends UseCase<Todo, QueryParams<Todo>> {
  GetTodoUseCase(this._repository);
  final TodoRepository _repository;

  @override
  Future<Todo> execute(QueryParams<Todo> params, CancelToken? cancelToken) async {
    cancelToken?.throwIfCancelled();
    return _repository.get(params);
  }
}
```

The `usecase` plugin applies a **source interface guard** (`SourceInterfaceGuard`): before generating, it parses the repository/service interface file and drops methods whose action methods are not declared there. When the interface file is absent (same-plan generation), it fails open and records an interface expectation so the `zfa make` post-pass can verify the responsible plugin (repository/service) declared the methods. Rejected methods trigger a stale-test sweep that removes test files importing the now-non-existent use case files.

Sources: [entity_usecase_generator.dart](lib/src/plugins/usecase/generators/entity_usecase_generator.dart#L40-L120), [entity_usecase_generator.dart](lib/src/plugins/usecase/generators/entity_usecase_generator.dart#L230-L420), [usecase_plugin.dart](lib/src/plugins/usecase/usecase_plugin.dart#L1-L120), [get_todo_usecase.dart](example/lib/src/domain/usecases/todo/get_todo_usecase.dart#L1-L24)

## Custom Use Cases

When the operation is not a direct CRUD mapping, use a custom use case via `zfa usecase create <Name> --domain=<domain> --type=<type>`. Supported types: `usecase` (future), `stream`, `background`, `os_background`, `completable`, `sync`. Custom use cases depend on a repository (`--repo`) or service (`--service`) and delegate to a resolved method name. When the service declares a single method, that method is used; when it declares several, the one whose params/returns match the request is selected; otherwise the command refuses with a named fix rather than emitting non-compiling code.

Two composition patterns are supported:

- **Orchestrator** (`--usecases=...`): a use case that composes other use cases (and optionally a service/repository) and runs them together inside one `execute`. Useful for transactional multi-step operations.
- **Polymorphic** (`--variants=...`): an abstract base use case plus one concrete variant per variant name, plus a factory. Useful when the same operation has several implementations (e.g., per payment method).

Custom use cases can also declare multiple parameters (`--params` as a list), in which case a `*Params` data class is emitted alongside the use case.

Sources: [custom_usecase_generator_generate.dart](lib/src/plugins/usecase/generators/custom_usecase_generator_generate.dart#L1-L120), [custom_usecase_generator_orchestrator.dart](lib/src/plugins/usecase/generators/custom_usecase_generator_orchestrator.dart#L1-L80), [custom_usecase_generator_polymorphic.dart](lib/src/plugins/usecase/generators/custom_usecase_generator_polymorphic.dart#L1-L80), [custom_usecase_generator_methods.dart](lib/src/plugins/usecase/generators/custom_usecase_generator_methods.dart#L1-L90)

## Background & OS Background Tasks

`BackgroundUseCase` runs a `buildTask()` (which must be a static or top-level function) on a separate isolate and streams `Result<T, AppFailure>` back to the main isolate. Parameters must be serializable. It is not supported on web. The task communicates via `BackgroundTaskContext` (`sendData`, `sendError`, `sendDone`).

`OsBackgroundTaskUseCase` wraps OS schedulers (workmanager on Android/iOS/macOS): it exposes a `descriptor` (`OsBackgroundTaskDescriptor` with `OsBackgroundTaskSchedule`), an `execute(NoParams)`, and a static `callbackHandler` for the background isolate dispatcher. Android enforces a 15-minute minimum interval; iOS/macOS treat frequency as `earliestBeginDate`. Desktop/web registration is a no-op. Instance dependencies are not available in the background isolate — the handler must reconstruct them.

Sources: [background_usecase.dart](lib/src/domain/background_usecase.dart#L1-L80), [os_background_task_usecase.dart](lib/src/domain/os_background_task_usecase.dart#L1-L124), [os_background_task.dart](lib/src/domain/os_background_task.dart#L1-L120), [os_background_task_generator.dart](lib/src/plugins/usecase/generators/os_background_task_generator.dart#L1-L120)

## Conformance & Drift

`zfa usecase verify <Entity>` runs the conformance gate: it re-derives the prescribed per-method contract (class, base class, variant, result type, params type) from the same derivation generation uses, audits every generated file against it, and reports entity drift. The drift checker re-hashes the entity source recorded in the create receipt (`spec.sha256`) and fails when the current source diverges (changed or deleted) — a use case set generated from a since-edited entity is stale and must not stay green. The verify command exits non-zero with fix lines on failure.

Sources: [usecase_drift_checker.dart](lib/src/plugins/usecase/conformance/usecase_drift_checker.dart#L1-L80), [usecase_plugin.dart](lib/src/plugins/usecase/usecase_plugin.dart#L1-L60)
