# Data & DI Layer

The data layer handles external concerns: API communication, local persistence, caching strategies, and dependency injection wiring.

## Repository Pattern

Generated repositories follow Clean Architecture with domain interfaces and data implementations:

```
lib/src/
├── domain/
│   └── repositories/
│       └── product_repository.dart         # Abstract interface (domain layer)
└── data/
    ├── datasources/
    │   ├── product_remote_datasource.dart  # HTTP API calls
    │   └── product_local_datasource.dart   # Hive local storage
    └── repositories/
        └── data_product_repository.dart    # Implementation (coordinates sources)
```

### Generated Repository Interface

```dart
// domain/repositories/product_repository.dart
abstract class ProductRepository {
  Future<Result<Product, AppFailure>> get(String id);
  Future<Result<List<Product>, AppFailure>> getList(ListQueryParams params);
  Future<Result<Product, AppFailure>> create(Product product);
  Future<Result<Product, AppFailure>> update(Product product);
  Future<Result<void, AppFailure>> delete(String id);
}
```

### Generated Implementation

```dart
// data/repositories/data_product_repository.dart
class DataProductRepository implements ProductRepository {
  final ProductRemoteDataSource _remoteDataSource;
  final ProductLocalDataSource? _localDataSource; // null if no caching

  DataProductRepository(this._remoteDataSource, [this._localDataSource]);

  @override
  Future<Result<Product, AppFailure>> get(String id) async {
    try {
      final product = await _remoteDataSource.get(id);
      return Result.success(product);
    } catch (e, st) {
      return Result.failure(AppFailure.from(e, st));
    }
  }
  // ...
}
```

## Dual DataSource Caching Pattern

When `--cache` is enabled, the repository uses a **Dual DataSource Pattern** — orchestration between remote and local storage based on cache policy.

### Data Flow

```
get(id):
  1. Check cache policy: isValid(key)?
  2. If valid → try LocalDataSource.get(id)
  3. If cache miss → RemoteDataSource.get(id)
  4. Save to LocalDataSource, markFresh(key)
  5. Return data
```

### Cache Policies (`lib/src/core/cache_policies.dart`)

All implement the `CachePolicy` interface:

```dart
abstract class CachePolicy {
  Future<bool> isValid(String key);
  Future<void> markFresh(String key);
  Future<void> invalidate(String key);
  Future<void> clearAll();
}
```

| Policy | Duration | Storage | When to Use |
|---|---|---|---|
| `DailyCachePolicy` | 24 hours | Persistent (SharedPrefs/Hive) | Daily-refresh data |
| `AppRestartCachePolicy` | App session | In-memory | Transient data, session state |
| `TtlCachePolicy` | Configurable TTL | Persistent | Custom durations (e.g., 6 hours) |

### Local DataSource (Hive)

When using `--cache-storage=hive`, the local datasource is fully generated:

```dart
class ProductLocalDataSource with Loggable, FailureHandler {
  final Box<Product> _box;

  ProductLocalDataSource(this._box);

  Future<Product> save(Product product) async {
    await _box.put(product.id, product);
    return product;
  }

  Future<List<Product>> saveAll(List<Product> products) async {
    await _box.putAll({for (final p in products) p.id: p});
    return products;
  }

  Future<Product?> get(String id) async => _box.get(id);
  Future<List<Product>> getAll() async => _box.values.toList();
  Future<void> delete(String id) async => _box.delete(id);
  Future<void> clear() async => _box.clear();
}
```

## Dependency Injection

DI is **code-generated** (not runtime-discovered). The `di` plugin analyzes generated files and produces `get_it` registration functions.

### Generated Structure

```
lib/src/di/
├── service_locator.dart               # GetIt instance + setupDependencies()
├── index.dart                         # setupDependencies() aggregator
├── usecases/
│   └── product_usecase_di.dart        # registerProductUseCases(GetIt)
├── repositories/
│   └── product_repository_di.dart     # registerProductRepository(GetIt)
├── datasources/
│   └── product_datasource_di.dart     # registerProductDataSources(GetIt)
└── providers/
    └── product_provider_di.dart       # registerProductProviders(GetIt)
```

### Example Registration

```dart
// Generated by di plugin
void registerProductUseCases(GetIt getIt) {
  getIt.registerFactory<GetProductUseCase>(
    () => GetProductUseCase(getIt<ProductRepository>()),
  );
  getIt.registerFactory<GetProductsUseCase>(
    () => GetProductsUseCase(getIt<ProductRepository>()),
  );
  // ...
}
```

### DI Features

| Feature | CLI Flag |
|---|---|
| Generate DI registrations | `--di` |
| Use mock implementations | `--use-mock` (inject mocks instead of real implementations) |
| Modular DI files | `--modular-di` (per-domain DI files) |
| Create registrations for an entity/usecase | `zfa di create <Name>` (auto-wires per-method usecases) |
| Register an existing class | `zfa di register <ClassName>` (auto-detects the domain) |
| Verify bindings | `zfa di verify` — dangling `getIt<T>()` registrations fail with a `--> fix:` hint |

> The positional grammar `zfa di <UseCaseName>` was removed (#856): only the
> subcommand grammar above is live. `zfa di create|register` ship a
> `proof.v1` receipt under `.zfa/receipts/` (spec 0974) so `zfa proof
> check` covers standalone runs.

### RegistrationDetector

The `RegistrationDetector` (`lib/src/plugins/di/`) scans existing source files to infer what dependencies a UseCase needs, using import analysis to find repository, datasource, and service types.

## Offline-First Sync

When `--sync` is enabled, the `sync` plugin generates metadata stores and strategy factories.

### Sync Types (`lib/src/core/`)

| Type | File | Description |
|---|---|---|
| `SyncStatus` | `sync_status.dart` | pending, syncing, synced, failed, conflicted |
| `SyncOperation` | `sync_operation.dart` | create, update, delete |
| `SyncDirection` | `sync_direction.dart` | push, pull, bidirectional |
| `SyncStrategy` | `sync_strategy.dart` | PushOnlySyncStrategy, BidirectionalSyncStrategy |

### Sync Data Flow

```
Offline write:
  1. Write to LocalDataSource
  2. Create SyncMetadata record (status: pending)
  3. When online: SyncStrategy.process() → RemoteDataSource
  4. Update SyncMetadata (status: synced or failed)

Conflict resolution:
  - Bidirectional strategy: compare timestamps, last-writer-wins
  - Push-only strategy: local always wins
```

## CLI Generation Examples

```bash
# Repository + datasource
zfa make Product --preset=crud --methods=get,getList

# With caching (daily policy, Hive storage)
zfa make Product --methods=get,getList --cache --cache-policy=daily --cache-storage=hive

# With DI and mocks
zfa make Product --preset=crud --di --mock --use-mock

# With offline-first sync
zfa make Product --methods=get,getList --sync --bidirectional

# Full data layer
zfa make Product --preset=crud --cache --sync --di
```

## Change Guidance

- **Adding a new cache policy:** Create a class implementing `CachePolicy` in `cache_policies.dart` and add builder support in the cache plugin.
- **Extending DI generation:** The `RegistrationDetector` scans for import patterns — update it if new dependency types are introduced.
- **Custom data source types:** The datasource plugin generates remote (HTTP) and local (Hive) templates — these are meant as starting points for manual implementation.
- **Related tests:** `test/plugins/repository/`, `test/plugins/datasource/`, `test/plugins/di/`, `test/plugins/cache/`, `test/plugins/sync/`, `test/integration/`
