# 1126-state-verify-receipts-explain

- **Spec ID**: 1126-state-verify-receipts-explain
- **Created**: 2026-09-08
- **Source**: GitHub issue #1126 (A+ UPGRADE: state — add verify, receipts, --explain, config schema)
- **Type**: CLI hardening + provenance + machine surface
- **Priority**: P1

## Problem

The state plugin sits at C+ after spec 976. It has `--json` on
`zfa state create` (canonical `zuraffa.verdict.v1` envelope, SPEC 1105)
but every A+ sibling has grown gates the state surface still lacks:

1. **No verify gate** — `zfa cache verify`, `zfa provider verify`,
   `zfa service verify`, `zfa datasource verify` all exist; there is no
   `zfa state verify <Entity>`. Drift between a generated state class
   and the run that produced it (entity changed, state not regenerated;
   hand-edited state bytes) is undetectable by automation.
2. **No capability receipts** — `CreateStateCapability.execute()`
   writes no proof. The command layer writes a timestamped
   `state-create-<entity>-<timestamp>.json` receipt (issue #1138) but
   the capability path (MCP / make-context callers) ships nothing, and
   neither path writes the stable per-entity
   `.zfa/receipts/state-<entity>.json` document the verify gate needs
   as its contract. The receipt also lacks the entity source hash —
   the binding `zfa datasource verify` uses to detect "entity changed,
   artifact not regenerated".
3. **No `--explain`** — `zfa service create --explain` (SPEC 1127) and
   `zfa datasource create --explain` (spec #1131) describe the plan
   without generating; `zfa state create` generates or nothing.
4. **Empty configSchema** — `StatePlugin.configSchema` is the
   pre-#1122 `{'type': 'object', 'properties': {}}`, which silently
   accepts anything. The actual config inputs `generateWithContext`
   reads (`methods`, `no-entity`, `domain`) are undeclared, so
   `zfa make --state` cannot parse them as flags and JSON agents have
   no vocabulary.
5. **No provenance header** — datasource (spec #1131 order 5) and
   provider (spec #979) stamp `// GENERATED by zfa … — DO NOT EDIT BY
   HAND.` on every fresh emission; generated state files are
   indistinguishable from hand-written ones.

## Goal

Make `state` an A+ surface: a `zfa state verify <Entity>` drift gate
(receipt-driven, exit 0 clean / exit 1 with `--> fix:`), capability
receipts via the `proof.v1` envelope at
`.zfa/receipts/state-<entity>.json` binding the state file's sha256
AND the entity source hash, `--explain` on `zfa state create`, a filled
configSchema (`methods`, `no-entity`, `domain`) with a runtime
validator that rejects unknown keys, and provenance headers on every
generated state file.

## Success Criteria (measurable)

- **SC-1 (verify gate)** — `zfa state verify <Entity>` compares the
  current state class against the create receipt and reports, per
  contract method, match / stale / missing; exits 0 on clean, exits 1
  with at least one `--> fix:` line on drift (missing receipt, missing
  file, modified bytes, stale entity, missing method), exits 2 on
  usage. `--json` emits exactly one canonical `zuraffa.verdict.v1`
  envelope as the last stdout line.
- **SC-2 (capability receipts)** — `CreateStateCapability.execute()`
  writes a `proof.v1` receipt (same shape cache/route/tdd/service use)
  at `.zfa/receipts/state-<entity>.json` carrying the state file's
  sha256, the entity source hash (`entity_source.{path,sha256,bytes}`),
  the state class name and the contract methods. Dry runs never write.
  `zfa state create <Entity>` (CLI path) also produces the stable
  receipt; regeneration refreshes it in place (latest-wins).
- **SC-3 (explain)** — `zfa state create <Entity> --explain` outputs a
  block naming the output state class (`<Entity>State`), the output
  file, which state members are generated (copyWith, isLoading
  getters, hasError, ==, hashCode, toString), and which derivation
  methods are included — each requested method mapped to the
  `is<Continuous>` state member it generates — without writing any
  file. With `--json`, the envelope carries the `explain` block with
  verdict `skip`.
- **SC-4 (config schema)** — `StatePlugin.configSchema` declares
  `methods` (array of strings), `no-entity` (boolean), `domain`
  (string), matching the inputs `generateWithContext` reads.
  `validateStateConfig` rejects unknown keys, type mismatches, and an
  empty-schema `{}` outright (the #1122 refusal); the capability
  rejects a malformed config with `success: false` and a fix message.
- **SC-5 (provenance header)** — every freshly generated state file
  starts with the
  `// GENERATED BY zuraffa zfa state create — DO NOT EDIT BY HAND.`
  block including the generator version and a regeneration hint; the
  emission stays byte-identical across both entry points
  (`zfa state create` ≡ `zfa make --state`) and across runs, so the
  byte-identity gates (snapshot goldens, make-drift) keep passing.
- **SC-6 (no regressions)** — `--json` on state create keeps its
  canonical envelope shape (SPEC 1105 fields unchanged; additive
  `receipts` entries only); existing state suites stay green.

## Constraints

- Do not break `--json` on state create (SC-6 is a hard gate).
- Receipt path is `.zfa/receipts/state-<entity>.json` (snake_case
  entity, mirroring `datasource-<entity>.json`, spec #977).
- The timestamped `state-create-<entity>-<timestamp>.json` receipt
  (issue #1138) is additive-kept; SC-2b of spec 976 stays green.
- The provenance header must be deterministic per (entity, config):
  run-varying bytes would permanently break
  `state_snapshot_test.dart` and `state_make_drift_test.dart`. The
  header therefore carries the generator VERSION; the run timestamp
  provenance lives in the receipt's `at` field (machine-readable,
  sha256-bound). This mirrors the datasource/provider A+ precedent and
  is recorded as a deliberate deviation from the issue's verbatim
  "version and timestamp" wording.
- Targeted testing only: suites covering modified files, never the
  full suite (kernel-cache/disk discipline).

## Acceptance Criteria

- **AC-1** `zfa state verify <Entity>` reports drift or clean (exit
  0/1), with `--> fix:` lines on every finding and a `--json` envelope.
- **AC-2** `zfa state create <Entity> --explain` outputs the explain
  block (state class, derivation mapping, generated members) and
  writes nothing.
- **AC-3** `.zfa/receipts/state-<entity>.json` exists after
  `zfa state create` and after a capability-path `create`, carrying
  `state_sha256` + `entity_source` + `methods` + `state_class`.
- **AC-4** Generated state files contain the provenance header.
- **AC-5** Config schema rejects unknown keys (`validateStateConfig`
  returns a violation naming the key and the allowed vocabulary; the
  capability refuses the run).
