# Spec: 1128 — provider A+ upgrade (`--explain` + comprehensive error handling)

## Summary

The provider plugin is at B+. It has `--json` on `verify`, deterministic
receipts, an AST verifier, and provenance headers. The narrowest gap to
A+ is exactly two features: (1) a `--explain` flag on
`ProviderVerifyCommand` that emits a human-readable block describing which
provider methods are registered, which types are resolved, and the
verification verdict (with `--> fix:` hints when available); and (2)
wrapping the full `execute()` path in `CreateProviderCapability` in a
`try/catch` matching the `di/repository` pattern, returning
`ExecutionResult(success: false, ...)` on exception instead of letting
it propagate.

## Current State (B+ baseline)

- **`--json` envelope exists** (`lib/src/commands/provider_verify_command.dart`):
  emits `{schema:1, ok, entity, providerFile, interface, methods[],
  stubCount, findings[]}` — the #778 single-object convention. Verified by
  `provider_verify_test.dart` (test #5: `--json emits a single machine
  verdict object`).
- **AST verifier exists** (`lib/src/plugins/provider/provider_verifier.dart`):
  stub gate (any `UnimplementedError` construction in a method body) +
  conformance gate (interface methods ⊆ provider methods).
- **Receipts exist** (`.zfa/receipts/provider-<Entity>.json` with proof.v1
  digests, `interface`/`methods`/`stubCount`).
- **Provenance headers exist** (`// GENERATED by zfa provider`).

## Current State (gaps → A+)

- **No `--explain`**: `ProviderVerifyCommand` parses only `--json` and
  `--service`. There is no human-readable prose block beyond the existing
  terse `_printText` listing. A reader cannot, in one pass, see
  (a) which provider methods are registered, (b) which types are resolved
  (the entity, the interface, the provider class), and (c) the verdict
  with `--> fix:` hints inline.
- **Partial try/catch**: `CreateProviderCapability.execute()` calls
  `_generateFiles` directly without wrapping. The di analog
  (`CreateDiCapability.execute`) wraps `_generateFiles` in `try/catch`
  and returns `ExecutionResult(success: false, message: 'di create
  failed for $target: $e', ...)` on exception. The provider capability
  throws `StateError` straight to the caller (issue #768 service-missing
  path), which the existing test #3 asserts via `throwsA(isA<StateError>())`
  — the test currently *requires* the unhandled crash, which is the B+
  smell this spec fixes. The `_emitReceipt` helper is already wrapped
  best-effort (`try { ... } catch (e) { print('⚠️ ...'); }`); the outer
  `execute()` path is not.

## Orders

1. **`--explain` flag on `ProviderVerifyCommand`**: when passed, emit a
   multi-line human-readable block (after the existing verdict
   computation, BEFORE the exit code is set) describing:
   - the entity under verification,
   - the resolved Service interface name,
   - the provider file path,
   - the methods registered on the provider class (from the AST scan,
     i.e. `ProviderVerifyReport.methods` plus the surviving stub list —
     `stubFindings`),
   - the verification verdict (`ok`/`not ok`),
   - the `--> fix:` hints for every finding (or a clean `✅` line when
     there are none).
   `--explain` is mutually-tolerant with `--json` (the `--json` envelope
   shape MUST NOT change — when both are passed, `--json` wins on stdout
   and `--explain` text is suppressed; this preserves the machine-readable
   contract for CI). Default text output (neither flag) is unchanged.
2. **Wrap `execute()` in `try/catch`**: `CreateProviderCapability.execute`
   must catch any exception from `_generateFiles` (and the subsequent
   `_emitReceipt` path is already best-effort) and return
   `ExecutionResult(success: false, message: 'provider create failed for
   $name: $e', data: {'generatedFiles': const <GeneratedFile>[]})` —
   matching `CreateDiCapability.execute` exactly. The existing
   `throwsA(isA<StateError>())` test (#768) MUST be updated to assert
   `result.success, isFalse` + the actionable message contains
   `CartService` + `domain/services/cart_service.dart` +
   `zfa service create --name Cart` (the same diagnostics the
   `StateError` carried — they live in the message now).
3. **Test — `--explain` output** under `test/plugins/provider/provider_verify_test.dart`:
   - `--explain` emits a block containing the entity name, the interface
     name, the provider file, the registered method list, the verdict,
     and the `--> fix:` line on a failing case.
   - `--explain` on a clean provider emits the same block with a `✅`
     verdict line and no fix hints.
   - `--explain --json` together → `--json` wins (single machine object
     on stdout, no explain prose) — envelope shape unchanged.
4. **Test — error-handling path** under
   `test/plugins/provider/create_provider_capability_test.dart` (or the
   sibling file the implementer picks): simulate a missing provider file
   (the existing #768 path: service interface missing →
   `_generateFiles` throws `StateError`). Assert the new contract:
   `execute()` does NOT throw; it returns `ExecutionResult(success:false,
   message: contains 'CartService' + 'domain/services/cart_service.dart'
   + 'zfa service create --name Cart', files: [])`.

## Hard Constraints

- **Do not change the `--json` envelope shape.** `schema`, `ok`, `entity`,
  `providerFile`, `interface`, `methods`, `stubCount`, `findings` must
  remain exactly as in `ProviderVerifyReport.toJson` (verified by the
  existing `--json` test).
- **Do not change verifier semantics.** `ProviderVerifier.scanSource` and
  `ProviderVerifier.verify` keep their current behavior; `--explain` only
  changes the *presentation* of the resulting `ProviderVerifyReport`.
- **Failing-first** for the two new behaviors (`--explain` prose;
  error-handling `ExecutionResult`). Red evidence recorded in
  `tdd/test-list.md` + `tdd/cycle-log.md`.

## Acceptance Criteria (ALL must hold, all measurable)

- **AC-1**: `zfa provider verify <Entity> --explain` prints a
  human-readable block naming the entity, the resolved interface, the
  provider file, the registered methods, the verdict, and (when present)
  `--> fix:` hints. PROVED by a green test in
  `provider_verify_test.dart`.
- **AC-2**: `zfa provider verify <Entity> --json` continues to emit the
  unchanged `{schema:1, ok, entity, providerFile, interface, methods,
  stubCount, findings}` envelope. PROVED by the existing `--json` test
  still green.
- **AC-3**: `zfa provider verify <Entity> --explain --json` is dominated
  by `--json` (single machine object on stdout, no explain prose).
  PROVED by a green test.
- **AC-4**: A malformed entity (missing service interface — the #768
  path) does NOT crash with an uncaught `StateError`; it returns
  `ExecutionResult(success: false, message: ..., files: [])`. PROVED by
  a green test asserting `result.success, isFalse` and that `message`
  contains `CartService` + `domain/services/cart_service.dart` +
  `zfa service create --name Cart`.
- **AC-5**: The existing `provider_verify_test.dart` `--json` test and
  stub/conformance positive/negative tests remain green (no regression
  in verifier semantics).
- **AC-6**: `dart analyze` is clean on changed files; `dart test` on
  changed files is green; `dart format .` produces zero formatting
  diffs.
