# Feature Specification: Migrate `html_to_markdown_ffi` to be built on zuraffa

**Feature Branch**: `064-migrate-html-to-markdown-ffi`

**Created**: 2026-09-01

**Status**: Draft

**Input**: Issue [#687](https://github.com/arrrrny/zuraffa/issues/687) — "Migrate html_to_markdown_ffi to be built on zuraffa", a sub-issue of EPIC #214 ([v6] Migrate all ZikZak pub.dev packages to be built on zuraffa).

## Mission

Migrate the `html_to_markdown_ffi` pub.dev package — a Dart FFI bridge for HTML-to-Markdown conversion — from its current standalone Flutter/Dart implementation to a complete rewrite built on the zuraffa framework. This is one per-package migration under the EPIC #214 umbrella.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The package compiles and passes its test suite as a zuraffa-native package (Priority: P1)

A maintainer clones the migrated `html_to_markdown_ffi` repository, runs `dart pub get`, and runs the test suite. All tests pass. The package's directory structure, entity definitions, and data layer are generated and maintained through `zfa` commands (per the v5 canonical workflow), and the package's native FFI bindings for each platform compile successfully.

**Why this priority**: This is the fundamental success condition — the migrated package must be a working, testable zuraffa-native package.

**Independent Test**: Clone the repo, run `dart test`, verify all tests pass. Run `dart analyze` and verify zero warnings/errors.

**Acceptance Scenarios**:

1. **Given** the migrated repository, **When** `dart pub get` runs, **Then** all dependencies resolve without conflict.
2. **Given** a clean checkout, **When** `dart test` runs, **Then** all tests pass.
3. **Given** `dart analyze`, **Then** zero warnings and zero errors are reported.

---

### User Story 2 - The package is structured per the zuraffa v5 domain layout (Priority: P1)

A maintainer examining the package's source tree finds the canonical zuraffa v5 layout: entities under `lib/src/domain/entities/`, repositories and datasources in their respective layers, and use cases for business logic. All architecture is generated by `zfa make` with no hand-crafted bypass.

**Why this priority**: The point of the migration is to bring the package under the zuraffa framework's conventions — a working package in the wrong layout is not a complete migration.

**Independent Test**: Inspect the directory tree under `lib/src/domain/` and verify entities, repositories, and data sources follow the canonical v5 layout; confirm no entity or architecture file was hand-created outside the `zfa` workflow.

**Acceptance Scenarios**:

1. **Given** the migrated package, **When** `lib/src/domain/entities/` is inspected, **Then** each entity lives in `lib/src/domain/entities/<entity_snake>/<entity_snake>.dart` (the canonical v5 path).
2. **Given** the migrated package, **When** generated architecture files are reviewed, **Then** they were produced by `zfa make` commands (verifiable from commit history or `zfa` command logs) with no hand-written architecture files.

---

### User Story 3 - The FFI native bindings are preserved and integrated into the zuraffa data layer (Priority: P1)

A maintainer invokes the HTML-to-Markdown conversion functionality (the package's core capability) and it produces correct output. The FFI bindings for all supported platforms (iOS, Android, Windows, Linux, macOS) remain functional; the zuraffa data layer calls the native implementation through the existing FFI bridge.

**Why this priority**: The package's value is the FFI bridge — migrating the Dart scaffolding to zuraffa must not break the native bindings.

**Independent Test**: Run platform-specific tests (or a cross-platform integration test) that exercise the HTML-to-Markdown conversion end-to-end, verifying output quality across a corpus of HTML inputs.

**Acceptance Scenarios**:

1. **Given** a valid HTML input, **When** the package converts it to Markdown, **Then** the output matches the expected Markdown for that input.
2. **Given** the package on each supported platform, **When** the conversion function is called, **Then** it returns a result (no native binding errors) and the output is non-empty.
3. **Given** malformed HTML input, **When** the conversion function is called, **Then** it handles gracefully (returns a best-effort result or an error, not a crash).

---

### User Story 4 - Platform implementations follow EPIC #214 guidance (Priority: P2)

Per the EPIC #214 plan and the issue notes, platform implementations (Android, Windows, Linux, macOS) for `html_to_markdown_ffi` are covered by the umbrella `zikzak_inappwebview` package. This migration does not create separate platform sub-issues for those implementations.

**Why this priority**: Consistent with the parent epic's architecture decision to centralize platform implementations.

**Independent Test**: The migration spec does not introduce platform-specific FFI bindings outside those already in `zikzak_inappwebview`.

**Acceptance Scenarios**:

1. **Given** this migration, **When** platform-specific FFI implementations are reviewed, **Then** no new platform bindings are introduced outside `zikzak_inappwebview`.

---

### Edge Cases

- A platform (e.g., a new OS version) not currently supported by the existing FFI bridge: the migration does not add new platform support; it preserves existing capabilities only.
- A test that directly instantiates internal FFI types: such tests must be updated to go through the zuraffa data layer after migration.
- A pub.dev user who depends on `html_to_markdown_ffi`: the migration preserves the public API surface — no breaking changes to the package's published interface.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The `html_to_markdown_ffi` package MUST be restructured to follow the zuraffa v5 canonical layout (fixed domain root `lib/src/domain`, entities at `lib/src/domain/entities/<entity_snake>/<entity_snake>.dart`).
- **FR-002**: All entity definitions, repositories, datasources, and use cases MUST be generated and maintained through `zfa` commands (`zfa entity create`, `zfa make`, `zfa build`).
- **FR-003**: The package MUST retain all existing FFI bindings for iOS, Android, Windows, Linux, and macOS; migration MUST NOT remove or alter native binding logic.
- **FR-004**: The zuraffa data layer MUST call the existing FFI bridge for HTML-to-Markdown conversion; the FFI bridge is wrapped by the datasource layer, not replaced.
- **FR-005**: All existing tests MUST pass after migration, with no changes to test assertions beyond updating import paths to reflect the new layout.
- **FR-006**: The package's public API (the surface consumed by external dependents via pub.dev) MUST remain unchanged — migration is internal restructuring only.
- **FR-007**: Platform implementations for Android, Windows, Linux, and macOS MUST NOT be duplicated in this package; any platform-specific FFI logic for those platforms is sourced from `zikzak_inappwebview` per the EPIC #214 guidance.
- **FR-008**: The migrated package MUST publish to pub.dev under the existing `html_to_markdown_ffi` name with no version bump required solely by the migration.

### Key Entities

- **HtmlToMarkdownConverter** — the core conversion capability: accepts HTML string input, delegates to the native FFI bridge, returns Markdown string output.
- **ConversionResult** — the output entity: holds the converted Markdown string and any conversion metadata (error flag, input length, output length).
- **ConversionOptions** — configuration for the conversion (optional): controls behavior such as stripping HTML tags, preserving whitespace, etc.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All tests in the migrated package pass (`dart test` exit 0) with zero analysis warnings or errors (`dart analyze` clean).
- **SC-002**: The HTML-to-Markdown conversion produces output that matches the pre-migration behavior on a representative corpus of at least 20 HTML inputs across different categories (tables, lists, headings, links, images).
- **SC-003**: The migrated package compiles and tests pass on all five supported platforms (iOS, Android, Windows, Linux, macOS).
- **SC-004**: The migrated package is published to pub.dev with the same version, and dependent packages that import `html_to_markdown_ffi` continue to compile without changes.
- **SC-005**: No entity, repository, datasource, or use case file in the migrated package was hand-written — all were generated by `zfa` commands (verifiable from the commit that merges the migration).

## Out of Scope

- Adding new platform support beyond the five currently supported platforms.
- Changing the package's public API or adding new public functionality.
- Migrating the `zikzak_inappwebview` package itself — platform implementations are handled under that separate package.
- Updating dependent packages that consume `html_to_markdown_ffi` unless those updates are required solely by the migration (FR-006).

## Assumptions

- The existing `html_to_markdown_ffi` codebase is self-contained and does not depend on other ZikZak internal packages that have not yet been migrated.
- The `zikzak_inappwebview` package already contains the platform-specific FFI implementations for Android, Windows, Linux, and macOS, and the `html_to_markdown_ffi` package references or re-exports those implementations.
- The zuraffa version used for this migration is stable and the `zfa` commands (entity create, make, build) work reliably for a package of this type (Dart FFI with platform bindings).
- The migration does not require changes to the pub.dev publishing workflow — the package can be published as-is after the internal restructuring.
