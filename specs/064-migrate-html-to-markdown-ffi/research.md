# Research: Migrate `html_to_markdown_ffi` to zuraffa (spec 064, issue #687)

## D1 — Scaffold with `zfa package create-plugin`, no `--repo` override

- **Decision**: Run `zfa package create-plugin html_to_markdown_ffi --description "…"` (default
  platforms `android,ios,macos`; omit `--repo` so the generator's default owner `arrrrny` is
  stamped) with `--no-gate`, then run the per-package gate manually.
- **Rationale**: The generator (specs 1601/1602, issues #1604/#678) produces exactly the family
  shape the spec's FR-001 requires and the shape `zuraffa_auth`/`zuraffa_permissions` ship:
  app package, platform core, three adapters, zikzak publish scripts, test harnesses. The
  default owner constant `_repoOwner = 'arrrrny'` is correct; a hand-typed slug risks a typo
  (found during recon: a 5-r slug gets stamped verbatim).
- **Alternatives**: Hand-writing the monorepo (rejected: violates FR-002's generated-architecture
  requirement and drifts from the family shape); scaffolding under a different name
  (rejected: FR-008 requires publishing under `html_to_markdown_ffi`).

## D2 — Deliver in the existing repository, in place

- **Decision**: Scaffold into a temp dir, then graft `packages/`, `scripts/`, `PUBLISH.md` into
  `~/Developer/html_to_markdown_ffi` (the existing clone of `arrrrny/html_to_markdown_ffi`),
  preserving git history, root CHANGELOG.md, LICENSE, and the prebuilt `native/` binaries
  (which move into the adapters).
- **Rationale**: This is a migration of a published package (FR-008), not a green-field repo.
  Preserving history keeps the migration reviewable and the CHANGELOG continuous.
- **Alternatives**: Fresh repo + archive old one (rejected: loses history; SC-004 depends on the
  same published name/lineage).

## D3 — Where the FFI machinery lives in the family

- **Decision**:
  - `html_to_markdown_ffi_platform` hosts the transport seam (renamed from the generic
    `ChannelInvoke` envelope to conversion semantics), payload decode/typed-error mapping, the
    visitor vtable bridge plumbing (pure dart:ffi, shared by all adapters), and the
    `HtmNativeLibraryResolver` seam (lets the preserved `NativeLibrary` loader find adapter-bundled
    binaries).
  - Each adapter bundles its platform's prebuilt artifacts — android: `armeabi-v7a/arm64-v8a/x86_64`
    `.so`; ios: `ios-arm64/ios-sim-arm64/ios-sim-x64` `.a`; macos: `macos-arm64/macos-x64` `.dylib` —
    and implements the port over an injected channel whose default invoke performs the real FFI
    call on its host platform (guarded by `Platform.isX`), falling back to the typed
    `channel_not_wired` failure elsewhere (keeps adapter tests offline-green on CI hosts).
  - The app package keeps the preserved public loader (`lib/native_library.dart`) with its
    resolution chain intact (env var → bundled `native/` → resolver seam → cache → cargo workspace →
    open(name) → process()) so FR-003 ("MUST NOT remove or alter native binding logic") holds.
- **Rationale**: The binaries are the package's own prebuilt Rust bridge (upstream
  kreuzberg-dev/html-to-markdown); distributing them per-platform is precisely what federated
  adapters are for. FR-003's "retain all existing FFI bindings" reduces to the three platforms the
  package actually ships artifacts for — which equals the scaffold's default platform set.
- **Alternatives**: Keeping all binaries in the app package (rejected: defeats the federated split
  the user requested); sourcing binaries from `zikzak_inappwebview` (rejected: those are a
  different native library; spec FR-007 governs *not duplicating* platform bindings, and the
  existing bundled artifacts are this package's own existing bindings, protected by FR-003).

## D4 — Generated architecture vs. preserved public API (the boundary)

- **Decision**: The new zuraffa stack is generated: internal entities via `zfa entity create`
  (zorphy), repository/datasource/use case via `zfa make`, module/DI via the scaffold's
  registration pattern. The preserved public types (`ConversionOptions`, `ConversionResult`,
  `HtmlMetadata`, `ProcessingWarning`, enums, `Visitor`, exceptions) are kept verbatim as the
  compatibility surface and mapped at the service boundary to/from the internal entities.
- **Rationale**: FR-006 (public API unchanged) and FR-002/SC-005 (architecture generated by zfa)
  pull in opposite directions for the same class names; the only resolution that satisfies both
  is: public types = frozen compatibility layer (pre-existing code, protected by the spec),
  internal zuraffa stack = new zfa-generated code. The mapping is explicit and tested.
- **Alternatives**: Regenerating the public types as zorphy entities (rejected: breaks FR-006 —
  `ConversionOptions` is mutable with 40+ fields; zorphy output would change construction and
  behavior); declaring the whole package exempt from FR-002 (rejected: contradicts the spec's
  core mission).

## D5 — Sync + async on one port

- **Decision**: The port carries `Future<…> convert(...)` (canonical, envelope-wrapped — fits any
  transport) plus `… convertSync(...)` (the in-process fast path; adapters whose native library is
  in-process implement it; foreign adapters throw typed `sync_unsupported`). The preserved
  top-level `convert()` (synchronous, FR-006) uses `convertSync` through the service.
- **Rationale**: dart:ffi calls are synchronous; the pre-migration API is synchronous; the
  federated port contract is async. Both must coexist without breaking either.
- **Alternatives**: Making the public API async (rejected: breaking change, FR-006); dropping the
  async port (rejected: breaks the family contract that adapters/platform channels implement).

## D6 — Version and publish story

- **Decision**: Publish the migrated family at the next patch of the existing line (1.1.0 →
  **1.2.0**; pub.dev rejects re-publishing an existing version, so same-version publication is
  mechanically impossible — verify the live pub.dev version before preparing). App package first,
  then platform core, then android/ios/macos adapters, via the scaffold's
  `scripts/prepare_for_publish.sh` + `scripts/publish.sh` + `scripts/push_to_master.sh`.
- **Rationale**: FR-008 says "no version bump required *solely by the migration*" — but pub.dev's
  version-uniqueness rule forces a bump for any new content; 1.2.0 is the minimal honest bump.
- **Alternatives**: Publishing as 0.1.0 (the scaffold default; rejected: discards the existing
  version lineage); staying on 1.1.0 (rejected: `dart pub publish` refuses).

## D7 — Host-proof strategy (what "tests pass" means on this machine)

- **Decision**: The ported legacy suite runs in the app package on the macOS host against the real
  bundled dylibs through the macos adapter (sibling `dependency_overrides` in dev, stripped on
  publish). Android/iOS adapters are proven by offline structural tests (fake channels), matching
  the pre-migration status quo (the legacy suite also only executed on the host).
- **Rationale**: SC-003's "all five platforms" can only be *executed* on the platforms at hand;
  the other platforms keep compiling, loading-logic-preserving proofs and publish gates. This
  records honestly what is proven vs. structurally preserved.
- **Alternatives**: Device-farm runs (out of scope; pre-migration baseline never had them).
