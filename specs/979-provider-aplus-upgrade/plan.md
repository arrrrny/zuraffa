# Plan: 979 — provider A+ upgrade

## Approach

Four code seams, all red-first, mirroring the sibling A+ upgrades (978
service, 0971 route, 972 usecase):

1. **Provenance** — `ProviderBuilder` emits a `// GENERATED by zfa provider`
   header (fresh and append paths); `ProviderReceiptWriter` persists
   `.zfa/receipts/provider-<Entity>.json` (proof.v1 + interface/methods/
   stubCount extras) via a new `ReceiptStore.saveNamed`; the create
   capability and the make post-pass both emit it. `zfa proof check`
   re-derives the digests (already generic — the receipt format is what
   makes providers covered).
2. **Verify gate** — `ProviderVerifier` (pure Dart, AST-based):
   stub gate (any method body constructing `UnimplementedError`) and
   conformance gate (interface methods ⊆ provider methods, via
   `MethodExtractor`). Surfaced as `zfa provider verify <Entity>`
   (`--json` verdict, exit 0/1, `--> fix:` lines) and as a make post-pass
   hook: fresh stubs are recorded + named (visibility, no failure —
   stub-first semantics), a committed provider that still contains stubs
   fails the run; conformance misses always fail.
3. **Dead-flag purge** — `ProviderCommand` registers no plugin-specific
   parent flags; `init` + the `type` enum land in
   `CreateProviderCapability.inputSchema`; `ProviderPlugin.configSchema`
   advertises the same knobs (schema ≡ grammar). `PluginCommand` gains a
   `consumedParentFlags` override; `zfa manifest --verify [plugins...]`
   certifies every parent-level flag is live (consumed by run()) or absent.
4. **Tests** — 5 new files under `test/plugins/provider/` (stub gate,
   conformance, parity, receipts+proof round-trip, append/inject
   round-trip), failing first.
