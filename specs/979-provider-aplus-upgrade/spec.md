# Spec: 979 — provider A+ upgrade

## Summary

Make the provider plugin an A+ plugin: every generated provider carries
provenance (a `// GENERATED by zfa` header plus a deterministic
`proof.v1` receipt), surviving stub bodies can no longer hide (a
`zfa provider verify <Entity>` stub-escape gate plus a make post-pass hook),
the provider is AST-proven to implement every method of its target Service
interface, and the dead parent-level flag surface is purged and certified by
`zfa manifest --verify`.

## Current State (bugs)

- **No GENERATED marker** (`lib/src/plugins/provider/builders/provider_builder.dart`):
  emitted files carry no provenance header — `zfa proof check` cannot
  distinguish generated providers from hand-written ones, and no receipt
  records what was generated.
- **Stub bodies ship silently** (`provider_builder.dart:462-486`): every
  generated method is `UnimplementedError` + `logAndHandleError` with no
  marker, no receipt, no follow-up gate — the skeleton can reach production
  unnoticed.
- **Dead flag surface** (`lib/src/commands/provider_command.dart`): parent
  flags `--domain`, `--params`, `--returns`, `--type`, `--data`, `--init`
  are parsed but never read in `run()` (which only prints subcommand usage,
  bug #856) — flags that lie about what they control (#876 family). `init`
  is read by the create capability (`args['init']`) but missing from its
  `inputSchema`, so `zfa provider create --init` cannot even parse.
- **No conformance proof** that a provider satisfies its Service interface
  beyond downstream compilation.

## Orders

1. **GENERATED header + receipt**: emitted files get the standard
   `// GENERATED by zfa provider` header; `.zfa/receipts/provider-<Entity>.json`
   records interface, methods, and stub count; `zfa proof check` covers
   providers (green on fresh generation, red on hand-edit).
2. **Stub-escape gate**: `zfa provider verify <Entity>` (and a make post-pass
   hook) fails — exit 1 + `--> fix:` naming file + method — when a committed
   provider still contains `UnimplementedError` method bodies. Stubs are
   allowed to exist (fresh generation keeps stub-first semantics and records
   them in the receipt); they are not allowed to hide.
3. **Wire or delete dead parent flags**: every plugin-specific parent flag is
   removed from `ProviderCommand` (the subcommand grammar synthesized from
   the create capability `inputSchema` is the single live surface); `init`
   is wired into that schema; `zfa manifest --verify` certifies the flag
   surface afterward.
4. **Provider-conformance check**: after generation, AST-verify the provider
   implements every method of its target Service interface; a missing method
   → exit 1 + `--> fix:` (the provider analog of the #921 guard).
5. **Tests**: stub gate positive/negative, conformance positive/negative,
   append/inject round-trip, receipt emission — all failing-first under
   `test/plugins/provider/`.

## Hard Constraints

- Do not change generated body semantics (stays stub-first — the TDD flow
  fills them).
- Failing-first tests under `test/plugins/provider/`.

## Acceptance Criteria (ALL must hold)

- AC-1: Generated files carry provenance; proof check green on fresh
  generation, red on hand-edit — tested.
- AC-2: A surviving `UnimplementedError` provider fails `provider verify` —
  tested both ways (stub gate positive/negative).
- AC-3: No dead flags remain (grep-proven; schema/grammar parity test);
  `zfa manifest --verify provider` certifies the surface green.
- AC-4: Conformance check catches a missing interface method — tested
  positive/negative.
