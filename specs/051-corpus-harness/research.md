# Research: `zfa tdd corpus` — batch driving, provenance audit, gap ledger

## R1: How does `zfa tdd run` / `zfa tdd verify` expose machine-readable outcomes?

**Decision**: Spawn as sub-processes, parse stdout summary lines.

**Rationale**: Both commands already emit machine-readable final lines:
- `run: feature=<f> result=<r> pending=<n> red=<n> green=<n> done=<n>`
- `mutation: gate=<g> killed=<n> survived=<n> timed_out=<n> mutation_was_run=<n>`

The corpus runner spawns each as a `dart run` sub-process (via the existing
`StepRunner` pattern or a thin wrapper), captures stdout, and parses the
final summary line for the outcome. Exit code 0 = success; non-zero = stop.

**Alternatives considered**:
- Direct library calls (import RunCommand, call run()): rejected because
  the commands set `exitCode` via the process-global and print to stdout;
  sub-process isolation matches real CLI use and avoids side effects.
- IPC/socket protocol: overkill for a CLI tool; summary lines are stable.

## R2: Corpus progress store — JSON file vs per-feature directories?

**Decision**: Single JSON file at `.zfa/corpus/progress.json`.

**Rationale**: The corpus has ~120 features; a single file with a map of
feature→state is simpler than 120 individual files. Atomic writes via
temp+rename (same pattern as `RunStateStore`) prevent corruption. The
in-flight marker is a field in the same file (corpus-level, not per-feature),
matching the spec's "corpus-level in-flight marker" (FR-010).

**Alternatives considered**:
- Per-feature progress files: more files to manage, harder to get a
  global resume point; unnecessary for 120 features.
- SQLite: overkill; the corpus is file-based and the state is small.

## R3: Gap ledger — JSON array vs JSONL?

**Decision**: JSON array at `.zfa/corpus/gap-ledger.json`.

**Rationale**: The ledger is append-only but read infrequently (status,
report). A JSON array with atomic write (temp+rename) is simpler to
parse and inspect than JSONL. Entries are never edited — new entries
for resolved gaps are appended alongside the original entry.

**Alternatives considered**:
- JSONL (append-only by nature): simpler appends but harder to read
  as a whole; the ledger is small enough that full-file rewrite is fine.
- SQLite: overkill for an append-only log.

## R4: Provenance audit — how to attribute `lib/` files?

**Decision**: Three sources, unioned:
1. **Cycle logs** (`tdd/cycle-log.md`): the `make` step records which
   files were generated. Parse green entries for file paths.
2. **Setup/import provenance**: the corpus import (#627) records which
   `spec.md` files were copied. Scaffold files (`main.dart`, app shell)
   are attributed to the setup command.
3. **Carve-out manifest** (`.zfa/corpus/carve-out.json`): manually
   declared exemptions for UI files not generated by zfa.

A file not in any source is unattributed and fails the audit by name.

**Rationale**: This covers the spec's requirement that both loop-generated
and setup/import-provenance files are attributable. The carve-out manifest
is the sole exemption path, versioned and explicit.

**Alternatives considered**:
- Git history (blame): not reliable for generated files; the cycle log
  is the authoritative record of zfa invocations.
- File hash matching: fragile; the log is the contract.

## R5: Concurrent corpus run guard

**Decision**: Corpus-level in-flight marker in `progress.json`.

**Rationale**: Same pattern as `RunStateStore.refusalReason()`: the
progress file records `{ "in_flight": true, "owner_pid": <pid> }`. A
second `corpus run` checks this on startup and refuses if the pid is
alive. The marker is cleared on normal completion or on crash recovery
(pid dead).

**Alternatives considered**:
- Lock file (`.zfa/corpus/LOCK`): same semantics, less structured;
  JSON is consistent with the rest of the state.
- OS-level file lock (`flock`): not portable across macOS/Linux cleanly.

## R6: How does the runner invoke per-feature commands?

**Decision**: `dart run bin/zfa.dart tdd run <feature> --project <root>`
and `dart run bin/zfa.dart tdd verify --feature <feature> --project <root>`.

**Rationale**: The `--project` flag on both commands (already supported)
lets the corpus runner pass the target project root without changing CWD.
The `--zfa-bin` flag on `run` allows injection of a scripted fake for
tests. The corpus runner uses the same `zfa-bin` or defaults to the
package's own entrypoint.

**Alternatives considered**:
- Direct function calls: rejected per R1 — sub-process isolation is
  the designed boundary.
- Shell scripts: non-portable, harder to test.

## R7: Waiver mechanism for verify gate outcomes

**Decision**: Explicit waiver entries in `progress.json` per feature.

**Rationale**: A waived feature records `{ "waived": true, "reason": "...",
"actor": "...", "when": "..." }` alongside its `done` state. The runner
checks for a waiver before stopping on a non-PASS gate. Waivers are visible
in `corpus status` output and the final report — never silent.

**Alternatives considered**:
- Command-line flag `--waive <feature>`: one-shot, not persisted;
  the waiver must survive resumes and be visible in reports.
- Separate waiver file: adds a file; in-progress is the natural home.
