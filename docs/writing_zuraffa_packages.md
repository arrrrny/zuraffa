# Writing Zuraffa Packages

A Zuraffa-native package is a reusable, domain-oriented library that follows
the standard Zuraffa layout and **contributes architecture to consuming apps
via auto-registration** — entities, datasources, repositories, usecases,
agent tools — with zero manual wiring on the app side. This guide walks the
full lifecycle: create, generate, consume (spec 025 / issue #389).

The toy reference implementation lives in
[`examples/notes_package`](../examples/notes_package) (the package) and
[`examples/reference_package_app`](../examples/reference_package_app) (the
consuming demo). Every command below was verified against it.

## 1. Create the package

```bash
zfa package create notes_package
```

This scaffolds the standard layout:

```text
notes_package/
├── pubspec.yaml                  # zuraffa ^6.x + zorphy deps, v6 constraints
├── zfa.yaml                      # package-mode marker (see §3)
├── build.yaml                    # zorphy + json_serializable builders
├── analysis_options.yaml
├── lib/
│   ├── notes_package.dart        # public barrel
│   └── src/
│       ├── domain/{entities,repositories,usecases}/
│       ├── data/{datasources,repositories}/
│       ├── module/notes_package_package_module.dart   # runtime module
│       └── di/notes_package_package_registrar.dart    # package registrar
└── test/package_smoke_test.dart  # test harness
```

The scaffold passes `dart analyze` and the `zfa build` codegen pipeline with
**zero manual edits** — a module-only package (no entities) is a valid
starting point.

Options:

| Flag | Effect |
|---|---|
| `--output <dir>` | Parent directory for the new package (default `.`) |
| `--description <text>` | pubspec + README description |
| `--zuraffa-path <path>` | Pin zuraffa as a **path dependency** (develop the package against a local zuraffa checkout) instead of the published version |
| `--dry-run` | Preview the file list without writing |

Running `zfa package create` against an existing directory fails with a
clear error and never overwrites content. Package names must be
`snake_case` (`^[a-z][a-z0-9_]*$`).

> **Local development**: inside the zuraffa repo, the reference package was
> created with
> `zfa package create notes_package --output . --zuraffa-path ../..`
> run from `examples/`.

## 2. Generate architecture inside the package

The same commands you already use in an app — nothing new to learn:

```bash
cd notes_package
zfa entity create -n Note --field id:String --field body:String
zfa make Note datasource repository usecase di --mock --use-mock
zfa build
dart test
```

What differs from an app is the **emission shape**, not the commands:

- `zfa make ... di` updates **`lib/src/di/notes_package_package_registrar.dart`** —
  a standalone registration unit aggregating every contributed
  datasource/repository/usecase — instead of the app pair
  (`di/index.dart` with `setupDependencies` + `di/service_locator.dart`).
- App-only artifacts are **suppressed** in package mode: no routes, no app
  service locator, no presentation, no app shell (`zfa app shell` refuses
  with a clear error).
- The domain/data layers are byte-identical to what the same entity
  generates in an app — only DI registration and presentation differ
  (verified by the SC-003 parity test: ≥90% identical, actual 100% on the
  shared layers).

The registrar looks like:

```dart
// Generated by zfa — package registrar for notes_package (spec 025, FR-004).
void registerNotesPackage(ZuraffaDIContainer di) {
  final getIt = di.getIt;
  registerAllUseCases(getIt);
  registerAllDataSources(getIt);
  registerAllRepositories(getIt);
}
```

It is regenerated from the full set of category indexes on every
`zfa make ... di` run — multiple entities aggregate into the one registrar
in a single pass, with no cross-entity ordering assumptions.

The generated datasource methods are intentionally `UnimplementedError`
extension points. Ship a real implementation (or, for demos/tests, the mock
datasource via `zfa make ... --mock --use-mock`, as the reference package
does).

## 3. The package-mode marker

`zfa.yaml` at the package root is the package-shape marker the pipeline
reads:

```yaml
package_mode: true
```

It suppresses app-specific codegen and switches DI emission to the package
registrar. The marker deliberately does **not** live in `build.yaml`:
build_runner strictly validates that file's schema and rejects unknown
top-level keys, which would break every subsequent build. Any project with
`package_mode: true` gets package-mode behavior — including one you
assembled by hand rather than via the scaffold.

## 4. Author the module (your hand-edit zone)

`lib/src/module/<name>_package_module.dart` is the package's runtime module
— the only file you routinely edit after scaffolding. The scaffold emits a
working minimal module; you extend it with agent tools and lifecycle logic:

```dart
class NotesPackageModule extends PackageModule {
  @override
  String get zuraffaSdkConstraint => '^6.1.0'; // stamped at create time

  @override
  String get pluginId => 'notes_package';      // stable identifier

  @override
  void registerDependencies(ZuraffaDIContainer di) =>
      registerNotesPackage(di);                // the package registrar

  @override
  Map<String, ZuraffaRouteHandler> get routes => const {};

  /// Agent tools (§6): built against the consuming app's container.
  @override
  List<McpTool> buildAgentTools(ZuraffaDIContainer di) => [
    PackageUseCaseTool<GetNoteUseCase>(
      name: 'get_note',
      description: 'Fetches a note by query params.',
      container: di,
      invoke: (usecase, args) async => usecase.execute(
        QueryParams<Note>(params: {...}), null,
      ),
    ),
  ];
}
```

Export your public surface through the barrel (`lib/<name>.dart`): the
module, the registrar, and the domain types consuming apps use (see
[`examples/notes_package/lib/notes_package.dart`](../examples/notes_package/lib/notes_package.dart)).

## 5. Consume the package in an app

Add the dependency, import the barrel, and **activate the module** — that
is the entire integration:

```dart
import 'package:zuraffa/zuraffa.dart';
import 'package:notes_package/notes_package.dart';

Future<void> main() async {
  final engine = ZuraffaEngine()..registerPackage(NotesPackageModule());
  await engine.bootstrap();  // registerDependencies → onInit, per module
  await engine.ready();      // onReady, registration order

  // Resolves through auto-DI — no registration code anywhere in the app:
  final note = await engine.di
      .get<GetNoteUseCase>()
      .execute(QueryParams<Note>(params: {'id': 'id 1'}), null);

  await engine.shutdown();   // onDispose, reverse order
}
```

What the app gets for free:

- **Auto-DI (FR-005)**: the module's `registerDependencies` runs the
  package registrar during `bootstrap()` — the app's container resolves the
  package's datasources, repositories, and usecases with zero manual
  registration. Registration is strictly import-scoped: a package the app
  does not activate contributes nothing.
- **Lifecycle (FR-006/007)**: `bootstrap()` → `registerDependencies` +
  `onInit`; `ready()` → `onReady`; `shutdown()` → `onDispose` (reverse
  order). Modules initialize and dispose independently; query
  `engine.activeModuleIds` for the discoverable identifiers.
- **Version gating (FR-015)**: `registerPackage` validates the module's
  `zuraffaSdkConstraint` against the running zuraffa version — a
  major-version mismatch throws a `StateError` naming both versions before
  anything registers; a newer-minor package logs a warning.

Merging several packages is the same story per package: register each
module; each registrar contributes into the one shared container. Identity
conflicts surface as the container's existing clear registration errors
during `bootstrap()` — fix the conflict (or rename) rather than overriding
silently.

## 6. Agent tools, namespaced

Tools generated inside a package surface in the consuming app's tool
registry under `<package>.<tool>`:

```dart
final tools = McpToolRegistry();
PackageAgentTools.registerInto(tools, NotesPackageModule(), engine.di);

await tools.find('notes_package.get_note')!.call({'params': {'id': 'id 1'}});
```

- `PackageUseCaseTool` wraps any usecase: it resolves the usecase from the
  container (the package's own dependency context) and returns a standard
  `McpToolResult`; failures surface as `isError` results, never throws.
- Two packages contributing the same tool name coexist (`a.get_note`,
  `b.get_note`). Registering the same package twice fails loudly.
- Tools are absent from the registry until the app registers them — no
  global side effects.

> Per-usecase agent-tool **codegen** (`zfa make --agent`) is tracked
> separately in issue #385 (spec 029). Until it lands, wire tools via
> `buildAgentTools` as the reference package shows — the runtime bridge
> (namespacing, registry, collision safety) is complete.

## 7. Build & release

```bash
zfa build          # same pipeline as an app (guard → codegen → safety nets)
dart analyze       # zero errors expected
dart test
```

`zfa build` works identically in package and app context (FR-010): the
pre-flight build.yaml guard, the zorphy/json_serializable codegen, and the
post-build safety nets (zero-output detection, declared-parts check,
`dart analyze` on `lib/`) all run the same way. Before publishing, replace
the `publish_to: none` line and the (if used) path dependency on zuraffa
with the published version constraint stamped in your pubspec.

## Quick reference

| Concern | Where |
|---|---|
| Package-mode marker | `zfa.yaml` → `package_mode: true` |
| Scaffold command | `zfa package create <name>` |
| Registrar (generated) | `lib/src/di/<name>_package_registrar.dart` |
| Runtime module (yours) | `lib/src/module/<name>_package_module.dart` |
| Auto-DI entry | `engine.registerPackage(<Module>())` → `bootstrap()` |
| Lifecycle phases | `bootstrap()` → `ready()` → `shutdown()` |
| Agent tools | `PackageAgentTools.registerInto(registry, module, di)` |
| Version gate | `PackageModule.zuraffaSdkConstraint` |
| Reference package | `examples/notes_package` + `examples/reference_package_app` |
