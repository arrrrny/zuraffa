# Bug Assessment: fix(tdd): gen skips stub when binary changes — stale stub causes make regression

- **Slug**: issue-683-tdd-gen-stale-stub
- **Created**: 2026-09-01T14:09:44Z
- **Source**: https://github.com/arrrrny/zuraffa/issues/683
- **Verdict**: valid
- **Severity**: medium

## Report (verbatim or summarized)

`zfa tdd gen` skips regenerating a stub when the ownership check returns "reused/reused", even after the zfa binary has been rebuilt with a fix. This causes `zfa tdd make` to run against a stale stub, producing a false regression. Found while running `zfa tdd run` on forklift spec 004 with a freshly rebuilt binary (fix #657 for non-entity behaviors).

## Symptom

After `scripts/rebuild.sh` updates the zfa binary, a resumed `zfa tdd run` for a previously-generated behavior returns `ownership: reused/reused` and writes no bytes — but the stub on disk was generated by the old binary and is now stale. The subsequent `zfa tdd make` step compiles the test against the wrong stub content, producing a regression that a manual `dart test` confirms is a false failure.

## Reproduction

1. Run `zfa tdd run` on a spec — U1:gen produces stub v1, U1:verify-red certifies red.
2. Rebuild the binary: `bash scripts/rebuild.sh` (binary now emits different stub content).
3. Run `zfa tdd run` again on the same spec — U1:gen returns `ownership: reused/reused`, skips stub regeneration.
4. U1:make runs the test against the old stale stub — test still fails → false regression.
5. Manual `dart test test/tdd/u1_test.dart` passes (confirms stub is stale, test is correct).

## Suspected Code Paths

- `lib/src/plugins/tdd/services/artifact_registry.dart:98–171` (`preflight()`) — the core bug location. Returns `Ownership.reused` whenever a prior record exists for the same `behaviorId` and both files exist on disk. **Has no check for binary state.**
- `lib/src/plugins/tdd/models/artifact_record.dart` — `ArtifactRecord` has no field for binary metadata (`binaryMtime`, `binaryHash`, or equivalent). **No binary metadata is ever persisted.**
- `lib/src/plugins/tdd/commands/gen_command.dart:167` — `if (record.testOwnership != Ownership.reused && !dryRun)` — the guard that prevents writing when preflight returns `reused`. Skips both test and subject writes without any binary-freshness check.
- `lib/src/plugins/tdd/services/step_runner.dart:84–128` (`defaultZfaBin()`) — resolves the binary path to `Platform.script` (basename `zfa.dart`/`zuraffa.dart`), which gives the `File` path needed for mtime comparison. This path is already available at gen time.

## Root Cause Hypothesis

**Confidence: high.**

The ownership contract (spec 044) ties stubs to the generating binary. `preflight()` correctly detects a repeat `gen` call and returns `reused` — but it has no mechanism to detect that the generating binary has changed since the stub was written. The stub content is a function of the binary, so a binary update makes the existing stub stale. The `ArtifactRecord` model stores no binary metadata (no mtime, hash, or version), so the registry cannot distinguish "same binary, same stub" from "old binary, stale stub".

## Proposed Remediation

**Preferred**: Store the binary's modification time in `ArtifactRecord` and compare it in `preflight()`.

1. Add `binaryMtime` (ISO-8601 string) to `ArtifactRecord` (`artifact_record.dart`).
   - Persist it in `toJson()` / `fromJson()`.
   - Bump the `artifacts.json` schema; existing records with `null`/`missing` binaryMtime are treated as "binary unknown — skip freshness check."

2. In `GenCommand.run()` (`gen_command.dart`), capture the binary's mtime before `preflight()`:
   ```dart
   final binaryPath = Platform.script.toFilePath();
   final binaryMtime = (await File(binaryPath).stat()).modified.toUtc().toIso8601String();
   ```
   Pass it into the record. This requires threading `binaryMtime` through `ArtifactRecord` construction.

3. In `preflight()` (`artifact_registry.dart`), when a prior record exists, compare stored `binaryMtime` against the current binary's mtime. If the binary is newer, return `Ownership.created` (force regeneration) rather than `Ownership.reused`. Log a note: `"binary updated since last gen — regenerating stub"`.

4. Add a `--force` flag to `GenCommand` so users can explicitly bypass the binary check.

**Alternative A** (minimum viable — lowest risk): Instead of comparing mtimes in `preflight()`, emit a **warning** when `reused` and binary mtime > stub mtime:
```
warning: stub was generated by an older binary (stub mtime < binary mtime);
regenerate with `zfa tdd gen <id> --force` to update.
```
This avoids any schema change but still lets the user understand the regression.

**Alternative B** (most robust — highest effort): Hash the binary's output for the specific behavior (`zfa tdd func <id>`) and compare content, not just mtime. Option A/B from the issue.

**Files likely to change**:
- `lib/src/plugins/tdd/models/artifact_record.dart` — add `binaryMtime` field + JSON serialization
- `lib/src/plugins/tdd/services/artifact_registry.dart` — compare mtimes in `preflight()`
- `lib/src/plugins/tdd/commands/gen_command.dart` — capture binary mtime + add `--force` flag
- `test/plugins/tdd/commands/gen_command_test.dart` — add test for binary-mtime-based regeneration
- `test/plugins/tdd/models/artifact_record_test.dart` — add JSON round-trip for new field
- `test/plugins/tdd/services/artifact_registry_test.dart` — add preflight mtime-differ test

**Tests to add or update**:
- `gen_command_test.dart`: test that repeat `gen` with binary newer than stored mtime returns `Ownership.created`, not `reused`.
- `artifact_registry_test.dart`: test `preflight()` returns `created` when prior record exists but stored `binaryMtime` differs from current.
- `artifact_record_test.dart`: test JSON round-trip with `binaryMtime`.

## Risks & Considerations

- Schema migration: existing `artifacts.json` entries lack `binaryMtime`. Treat missing/null as "skip check" (backwards-compatible).
- Binary path: `Platform.script` resolves to the actual running binary. In JIT mode this is `bin/zfa.dart`; in compiled mode it may be a snapshot. mtime changes on rebuild for both cases.
- Performance: `File(binaryPath).stat()` is a single syscall — negligible overhead.
- The `--force` flag is a useful escape hatch and low implementation cost.
- The warning-only alternative (minimum viable) is strictly additive and zero-risk.

## Open Questions

- [RESOLVED: binary path is `Platform.script` — already available via `defaultZfaBin()` logic in `step_runner.dart`.]
- [NEEDS CLARIFICATION: should `preflight()` return `Ownership.created` or a new `Ownership.reusedNeedsUpdate` variant when the binary has changed? The former is simpler; the latter is more expressive.]
- [NEEDS CLARIFICATION: should the binary check apply only to the subject stub, or also to the test file? The test content may also change if the binary's template changes.]
