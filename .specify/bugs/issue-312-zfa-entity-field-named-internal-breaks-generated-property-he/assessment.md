# Bug Assessment: zfa entity: field named 'internal' breaks generated property helpers (meta.internal collision)

- **Slug**: issue-312-zfa-entity-field-named-internal-breaks-generated-property-he
- **Created**: 2026-08-22T19:42:20.566186+00:00
- **Refined**: 2026-08-22
- **Source**: https://github.com/arrrrny/zuraffa/issues/312
- **Verdict**: valid, but **already fixed upstream** — no zuraffa change required
- **Severity**: was high (blocked 9 Vendure entities); now resolved

## Report (verbatim or summarized)

A nullable field named `internal` made the generated helpers (`hasInternal`,
`noInternal`, `internalRequired`) resolve the bare identifier `internal` to the
top-level `internal` const re-exported from `package:meta/meta.dart` (via
`zorphy_annotation`), typed `Object` — so `internalRequired` failed to compile:
"A value of type 'Object' can't be returned ... return type 'bool'".

## Symptom

`dart analyze` errors in `<entity>.zorphy.dart` for the property helpers of any
nullable field whose name collides with a top-level symbol exported by
`meta`/`zorphy_annotation`.

## Suspected Code Paths

- The failing code is **generated by zorphy**, in
  `zorphy/lib/src/generators/property_helper_generator.dart` (methods
  `has<X>`, `no<X>`, `<x>Required`, lines ~112-170).
- zuraffa contains **no** property-helper generator:
  `grep -rn "Required" lib/src/plugins lib/src/commands` returns only
  `inject_builder.dart`'s unrelated `_isRequired(...)` parameter check. The
  `*Required` getters visible under `lib/src/core/params/*.zorphy.dart` are
  checked-in *output* of the zorphy builder, not generator source.

## Root Cause Hypothesis

The generator emitted unqualified `$fieldName` in the helper bodies, so name
resolution could pick a library-level import over the instance member. The fix
is to emit `this.$fieldName`.

## Proposed Remediation

None in zuraffa — the upstream fix is already released:

- zorphy commit `c4704f1` — "fix(generator): escape enum-reserved field names +
  this.-qualify property helpers" (present in the `arrrrny/zorphy` history).
- Verified in the **published** package that zuraffa depends on
  (`zorphy: ^2.2.0`, resolved to `zorphy 2.2.0` in `pubspec.lock`):
  `~/.pub-cache/hosted/.../zorphy-2.2.0/lib/src/generators/property_helper_generator.dart:131,141,166`
  all emit
  `"return this.$fieldName ?? (throw StateError('$fieldName is required but was null'));"`,
  and `has<X>`/`no<X>` emit `this.$fieldName != null` / `== null`.

With `this.`-qualification, the `meta.internal` top-level const can no longer
shadow the instance field, so the reported error cannot occur with the pinned
dependency.

## Files likely to change

None. (Fix already shipped in `zorphy 2.2.0`.)

## Tests to add

A regression test in zuraffa would require running the zorphy `build_runner`
builder over a fixture entity with an `internal:bool?` field. That belongs in
zorphy (where the generator lives) and is not runnable here — see risks. No
zuraffa-side unit test can meaningfully lock generator output it does not
produce.

## Risks & Considerations

- The sibling `../zorphy` checkout in this environment does not compile
  (`helpers.dart:894: 'ParameterElement' isn't a type.`), so `zfa build` /
  `zfa entity create` cannot be executed locally to demonstrate the generated
  output end-to-end. Verification was done by inspecting the resolved published
  generator source, which is what CI and users actually run.

## Outcome

**Skipped for this pass — nothing to fix in `zuraffa/lib/src`.** Recommend
closing issue #312 as fixed upstream (zorphy `c4704f1`, shipped in
`zorphy 2.2.0`, already the pinned dependency), noting the verification above.

## Open Questions

- Should zuraffa add a docs note that field names colliding with
  `meta`/`zorphy_annotation` top-level symbols are safe as of zorphy 2.2.0?
