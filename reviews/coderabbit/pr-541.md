## Actionable comments

### 1. 🩺 Stability & Availability · 🟠 Major · ⚡ Quick win
**Shared AOT exe build races under parallel `setUpAll`** — `test/helpers/run_zfa_source.dart`

`zfaExePath` is built into a single shared path `${zfaProjectRoot}/.dart_tool/zfa_cli_bin/zfa_exe` and reused by **every** test file that calls `initZfaSourceBin()`. Under `dart test -j4`, multiple files' `setUpAll` can invoke `_buildZfaExeIfPossible()` concurrently: both may observe "no exe" and launch `dart compile exe` to the same output file, or one process may `runZfaSource()` the binary while another is still writing it — producing flaky crashes or "exec format error". The `lastModified` reuse check does **not** serialize concurrent builds.

```dart
// run_zfa_source.dart — concurrent setUpAll can reach here simultaneously
final compile = await Process.run(
  'dart',
  ['compile', 'exe', zfaSourceBin!, '--output', exePath],
  workingDirectory: zfaProjectRoot,
).timeout(const Duration(seconds: 100));
```

**Proposed fix:** build into a per-test-file (or per-process) temp dir, or guard the build with a file lock (e.g. `package:file_lock` / a `.lock` sentinel) so only one process compiles while the rest wait on the finished artifact.

<details>

```diff
-  final exeDir = p.join(zfaProjectRoot, '.dart_tool', 'zfa_cli_bin');
+  // Per-process dir so concurrent setUpAll calls don't clobber each other.
+  final exeDir = p.join(
+    zfaProjectRoot, '.dart_tool', 'zfa_cli_bin',
+    'pid-${pid}',
+  );
```
</details>

🤖 **Prompt for AI Agents**
```
In test/helpers/run_zfa_source.dart, the AOT exe is written to a single shared
path used by all test files. Make the build location unique per process (e.g.
include the PID or use a temp dir) OR wrap _buildZfaExeIfPossible in a cross-process
file lock so concurrent setUpAll calls serialize. Ensure the resulting zfaExePath
is still reused within the same process.
```

### 2. 🩺 Stability & Availability · 🟡 Minor · ⚡ Quick win
**`_buildZfaExeIfPossible` leaks the compile process on timeout** — `test/helpers/run_zfa_source.dart`

`.timeout(const Duration(seconds: 100))` on `Process.run('dart', ['compile','exe', ...])` resolves with a `TimeoutException` that is swallowed by `on Object`, but the underlying `dart compile` child process is never killed and keeps running in the background. The comment claims "never leaks a hang into setUpAll", but the orphaned compile can linger well past the 100s boundary.

**Proposed fix:** use `Process.start` and `process.kill()` inside `onTimeout`, or track the `Process`/`ProcessResult` and kill it on timeout.

🤖 **Prompt for AI Agents**
```
In test/helpers/run_zfa_source.dart, replace the Process.run(...).timeout(...) call
in _buildZfaExeIfPossible with Process.start so that onTimeout can call process.kill()
to avoid leaving an orphaned `dart compile exe` process running after the 100s timeout.
```

---

### 3. 📐 Maintainability & Code Quality · 🔵 Trivial
**`_noPluginCommands` only matches `args.first`** — `lib/src/cli/cli_runner.dart`

Plugin boot is skipped only when the very first argument equals `xray`. A leading global flag (e.g. `zfa --verbose xray mock`) makes `args.first == '--verbose'`, so the optimization is silently skipped. Not a bug — just sub-optimal. Consider resolving the actual command name from parsed args rather than `args.first`.

🤖 **Prompt for AI Agents**
```
In lib/src/cli/cli_runner.dart, the skipPlugins check uses args.first. Make it
robust to leading global flags by resolving the top-level command name after
option parsing (or skipping flags before the first non-flag token) instead of
relying on args.first.
```
